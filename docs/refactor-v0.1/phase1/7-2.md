# Phase 1-7 remote revision／server ack 実装計画

## Summary

Cloud Functionsは導入せず、5 datasetすべてをFirestore transactionによる共通push契約へ移行する。競合はdocument単位の簡易LWWとし、端末で記録した`clientUpdatedAt`が新しいmutationを採用する。複雑なrebaseや競合UIは実装しない。

## Implementation Changes

- remote documentへ`revision`、`lastMutationId`、`clientUpdatedAt`、server timestampの`updatedAt`、`schemaVersion: 1`を追加する。MyWordは既存の`deletedAt`をtombstoneとして維持する。
- `SyncMutation`とoutboxへUTCの`clientUpdatedAt`を追加し、DBをv7へ移行する。既存outbox行は`createdAt`を初期値に使い、mutation統合時は最新の編集時刻へ更新する。
- 共通の`RemoteMutationRequest`と`RemoteMutationAck`を追加する。ackは`applied`、`duplicate`、`superseded`の結果、remote revision、remote lastMutationId、server updatedAtを返す。
- 5つのremote adapterをtransaction書き込みへ変更する。
  - `lastMutationId == mutationId`なら書き込まず`duplicate`を返す。
  - incoming `clientUpdatedAt`がremoteより古ければ書き込まず`superseded`を返す。
  - それ以外はfield maskだけを反映し、`revision + 1`とmetadataを保存して`applied`を返す。同時刻は後からtransactionを完了したmutationを採用する。
  - metadataのない既存documentは`revision = 0`、`clientUpdatedAt = updatedAt`、`schemaVersion = 1`として扱い、個別migrationは行わない。
- 各handlerはremote ack後、local rowの`remoteRevision`／`lastMutationId`更新とoutbox ackを同じDrift transactionで確定する。leaseやlocal revisionが変化していた場合は全体をrollbackし、remote側は次回の冪等再送で回収する。
- pull時もremote metadataをDriftへ保存する。`superseded` mutationはoutboxから除去し、同一cycleのpullでremoteの勝者をlocalへ反映する。
- MyWordはfield rebaseを廃止する。tombstoneはterminal扱いとし、通常更新では`deletedAt`を消さない。復元機能は今回追加しない。
- User profileの初期作成をmetadata付きtransactionへ統一し、通常編集はusernameだけをoutbox経由にする。emailはAuthの値、`subscriptionStatus`は初期値`free`からクライアント更新不可とする。
- `firestore.rules`を追加し、本人の`Users/{uid}`と4 subcollectionのみread/write可能にする。dataset別field allowlist、型、server timestamp、作成時revision 1、更新時revisionの1増加、ID不変、profile認可field不変、hard delete禁止を検証する。
- Firebase設定は実アプリ設定に一致する`my-dic-sync`へ統一し、`firebase.json`へRulesとFirestore Emulator設定を追加する。本番Rulesのdeployは自動実行せず、emulator検証後の明示的な配備手順として残す。
- [7-pre-phase2-convergence.md](C:\Users\deded\Documents\LocalDev\my_dic\docs\refactor\phase1\7-pre-phase2-convergence.md)と関連contextを更新し、MyWordのrebase要件を簡易LWWへ置換してStage 3の完了条件を実装内容に合わせる。

## Public Interfaces

- `SyncMutation.clientUpdatedAt: DateTime`を必須化する。
- remote patch APIは`Future<void>`と`isNew`を廃止し、mutation ID・時刻・field maskを受けて`Future<RemoteMutationAck>`を返す。
- local data sourceへremote metadataの保存APIを追加し、handlerがoutbox ackと一体で呼び出せるようにする。
- revisionはFirestoreでは整数、既存Drift列では10進文字列として保存し、不要なrow schema変更を避ける。

## Test Plan

- 共通contract testで初回write、revision増加、同一mutation再送、古いmutationの破棄、同時刻の後着優先、metadataなしdocumentからの移行を5 adapterへ適用する。
- handler testでserver commit後・local ack前の停止、再送、lease不一致rollback、新しいlocal editを保持したmetadata更新、`superseded`後のpull収束を確認する。
- MyWord testで古いupdateが新しい本文を上書きしないこと、tombstoneが通常updateで復活しないこと、より古いdeleteが新しいdocumentを隠さないことを確認する。
- DB migration testでv6→v7の`client_updated_at = created_at`補完と既存queueの保持を確認する。
- Firestore Emulator Rules testで他人のdocument拒否、未知field拒否、revision飛び越し拒否、clientによるserver timestamp偽装拒否、profile認可field変更拒否、正規transaction許可を確認する。
- 最終確認はRules emulator test、`flutter analyze`、import boundary check、`flutter test`を実行し、CIにもRules testを追加する。

## Assumptions

- 同時編集は稀であり、端末時計のずれを許容した簡易LWWで十分とする。
- `baseRemoteRevision`は診断情報として残してもよいが、書き込み可否には使用しない。
- status系も同じdocument単位LWWを使い、古いmutationの別fieldを救済するmerge/rebaseは行わない。
- Cloud Functions、競合UI、tombstone復元、既存remote documentの一括backfillは対象外とする。
