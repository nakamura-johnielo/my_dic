# Phase 1-2: import境界を文書化し、既存違反を凍結してCIで新規違反を防ぐ

- 状態: 未着手
- 優先度: 高 / 再発防止
- 依存タスク: [`1-create-composition-root.md`](1-create-composition-root.md)と並行可能
- 関連タスク: Phase 1-3〜1-6、[`../local_first/1-define-local-first-contract.md`](../local_first/1-define-local-first-contract.md)、[`../local_first/8-cut-over-and-remove-legacy-sync.md`](../local_first/8-cut-over-and-remove-legacy-sync.md)
- 元調査: [`FLUTTER_ARCHITECTURE_REVIEW.md`](../../FLUTTER_ARCHITECTURE_REVIEW.md) 7.1〜7.4

## 目的

Clean Architectureとfeature ownershipを人の注意だけに依存させず、禁止依存をCIで検出する。今回の完了条件は既存違反の解消ではない。導入時点で存在する違反を明示的なbaselineとして凍結し、baseline外の違反をPRに持ち込めない状態を作る。

## 現在の問題

調査時点で次が確認されている。

- feature間直接import: 70本、23方向
- 双方向feature依存: 4組
- domainからFlutter SDKへのimport: 19本
- `core`からfeatureへのimport: 23本
- 別featureのpresentation型をroute引数やUI部品として参照

フォルダ名はlayerを示すが、import規則がないため実際の依存方向と一致していない。

## 境界契約

```text
feature/presentation -> feature/application -> feature/domain
feature/infrastructure ---------------------> feature/domain/application port
feature/infrastructure/sync ----------------> sync/feature application port
app/bootstrap ------------------------------> feature実装
app/routing --------------------------------> pure route contract
core ---------------------------------------> featureへ依存しない
```

feature間連携は、所有featureのapplication/domain port、または明示されたapp-level orchestrationを通す。別featureの`presentation/**` importは禁止する。

初回の検査対象は、解釈のぶれが少なく機械判定できる次の規則に限定する。より細かな規則は、誤検知なく表現できることを確認してから追加する。

| Rule ID | 禁止する依存 | 例外 |
| --- | --- | --- |
| `domain_no_framework` | `**/domain/**` から Flutter、Riverpod、Firebase、Drift、GoRouter をimportすること | なし |
| `core_no_feature` | `lib/core/**` から `lib/features/**` をimportすること | `core/application/auth_lifecycle/**` と `core/application/effects/**` はPhase 1-4で移設するまでbaselineのみ |
| `no_cross_feature_presentation` | feature A の `presentation/**` から feature B の任意の内部実装をimportすること | `app/routing` のpure route contractのみ |
| `no_feature_cycle` | feature間依存グラフに循環を作ること | baselineにある循環のみ |
| `firebase_at_boundaries` | presentation、domain、通常application、通常Repositoryから Firebase/Firestore をimportすること | auth infrastructure、`app/bootstrap/**`、sync remote adapter |
| `sync_adapter_composition_only` | `app/bootstrap/**` 以外から feature の sync remote adapter / DI を直接import・resolveすること | テストfixtureのみ |

`generated`、`*.g.dart`、`*.freezed.dart`、`lib/__generated/**` は生成元でないため検査対象外とする。`test/**` は本体と同じimport検査の対象にするが、fixture内で意図的に違反を作る場合だけfixture専用ディレクトリを除外する。

## 凍結baselineの運用契約

baselineは「現在ある違反の許可リスト」ではなく「返済計画の対象台帳」である。CIは次の三分類を出力する。

- baseline一致: 既存違反。警告として表示し、CIを失敗させない。
- baseline外: 新規違反。CIを失敗させる。
- baselineにだけ存在: 解消済みまたは検査定義が変わった項目。CIを失敗させず、更新候補として表示する。

baselineの各レコードは `ruleId`、正規化済み`source`、正規化済み`target`、`introducedAt`、`owner`、`trackingIssue` を持つ。sourceとtargetの完全一致で照合するため、既存ファイルに別の禁止importを追加しても新規違反になる。`trackingIssue`なしの追加は禁止する。

baselineの追加・変更は、通常の機能PRでは行わない。必要な場合は理由、owner、返済issueを含む専用PRとし、レビュー担当者を必須にする。baselineからの削除は既存違反を直したPRでのみ行う。Phase 1ではbaselineを0にすることを完了条件にしない。以後のリファクタリングで減らし、対象ルールごとに0件になった時点でbaselineレコードを削除する。

## 実装プラン

1. **ルールをデータとして固定する**
   - `tool/import_boundaries/rules.json` にRule ID、対象パス、許可例外、外部packageパターンを置く。
   - `docs/architecture/import-boundaries.md` に上表、feature間連携の入口、baseline更新手順を移す。このタスク文書は導入計画として残す。
   - 相対importと`package:my_dic/...`を同じリポジトリ内の正規化パスに解決する。区切り文字は常に`/`へ正規化し、Windowsでも同じ結果にする。

2. **検査器を追加する**
   - 依存を増やさないDart CLI `tool/check_import_boundaries.dart` を追加し、`lib/**` と `test/**` のDart importを走査する。
   - import文字列、source、target、Rule ID、行番号をJSONと人間向けテキストで出力する。`--format=json`、`--baseline <path>`、`--update-baseline`、`--check` を用意する。
   - 依存グラフをfeature単位で構築し、SCCで `no_feature_cycle` を判定する。cycleは含まれるfeature集合を安定順序でID化する。
   - `--check` はbaseline外が1件でもあれば非0終了し、baseline未使用項目は終了コード0で報告する。baselineを更新するコマンドはCIでは実行しない。

3. **テストで検査器そのものを固定する**
   - `test/tool/import_boundaries/` に最小fixtureを置き、package import、relative import、Windows形式の入力、generated除外を検証する。
   - 各Rule IDについて「違反を検出する」「許可例外を通す」「baseline一致は通る」「同じsourceへの追加違反は失敗する」をテストする。
   - cycle fixtureは単方向・双方向・3 feature循環を含める。Firebase fixtureはauth infrastructure、bootstrap、sync remote adapterの許可と、それ以外の拒否を確認する。

4. **初回baselineを監査付きで作成する**
   - ローカルで `dart run tool/check_import_boundaries.dart --format=json` を実行し、出力を `tool/import_boundaries/baseline.json` としてコミットする。
   - 生成後に各レコードへownerと既存の追跡issueを付与する。追跡先が未作成なら、少なくとも `docs/refactor` の対応タスクを記録する。
   - baseline生成の差分をレビューし、検査対象外・例外・既存違反が意図どおりであることを確認する。ここではproduction Dartコードの違反を修正しない。

5. **analyzerとCIへ接続する**
   - `analysis_options.yaml` から `test/**` の除外を外す。生成コードだけは明示的な理由とともに除外を維持する。
   - `.github/workflows/quality.yml` を追加し、pushとpull requestで `flutter pub get`、`flutter analyze`、`dart run tool/check_import_boundaries.dart --baseline tool/import_boundaries/baseline.json --check`、`flutter test` を順に実行する。
   - workflowはbaselineファイルが変更されたPRでは、変更内容と更新手順の説明をPR本文で求める。ブランチ保護ではこのquality checkを必須にする。

6. **導入を検証し運用へ渡す**
   - fixtureに意図的な新規違反を入れた状態でcheckが失敗し、baselineにある既存違反だけでは成功することを確認する。
   - CIのログに新規違反、既存baseline違反、解消候補の件数を分けて表示する。
   - `README.md` または開発者向け文書から境界契約とローカル実行コマンドへリンクする。以後、新しいRuleの追加は「検査器test → baseline監査 → CI有効化」の順で行う。

## 変更予定ファイル

| パス | 変更 |
| --- | --- |
| `docs/architecture/import-boundaries.md` | 境界契約、例外、baseline運用を正本として追加 |
| `tool/import_boundaries/rules.json` | 機械判定するルール定義を追加 |
| `tool/check_import_boundaries.dart` | import正規化、ルール判定、cycle検出、baseline照合CLIを追加 |
| `tool/import_boundaries/baseline.json` | 導入時点の既存違反台帳を追加 |
| `test/tool/import_boundaries/**` | 検査器とfixtureのテストを追加 |
| `analysis_options.yaml` | `test/**` の除外を解除 |
| `.github/workflows/quality.yml` | analyzer、境界検査、testを必須化 |
| `README.md` | 開発者向けの実行コマンドと運用文書へのリンクを追加 |

## 受け入れ条件

- [ ] 許可・禁止依存、例外、generated code除外理由が文書化されている
- [ ] 既存違反がsource・target単位の監査可能なbaselineとしてコミットされている
- [ ] baseline外の禁止importまたは新しいfeature cycleでCIが失敗する
- [ ] baseline内の既存違反だけではCIが成功し、解消候補を表示する
- [ ] relative import、package import、Windows区切り、generated codeをfixtureで検証している
- [ ] `test/**` が analyzer と境界検査の対象である
- [ ] `flutter analyze`、境界検査、`flutter test` がCIの必須checkである
- [ ] baseline変更にはownerと追跡先が必要で、通常の機能PRでは追加しない運用が文書化されている

## 実行コマンド（導入後）

```powershell
flutter analyze
dart run tool/check_import_boundaries.dart --baseline tool/import_boundaries/baseline.json --check
flutter test
```

## LLMへの引き継ぎ事項

違反を直すために型を無条件で`core`へ移さない。まずownershipを決め、所有featureのportまたはapp-level contractを利用する。baselineは新規違反を隠すために更新せず、既存債務を可視化したまま新規流入を止めるために使う。
