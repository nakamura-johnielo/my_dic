# 移行順序7: 西日・日西WordStatusのdomain／applicationを統合する

- 状態: 実施前
- 対象: [`concept.md`](./concept.md) の「移行順」7
- 前提: [`6.plan.md`](./6.plan.md) のCatalog物理移動とlegacy graph撤去が実装・検証済み
- 成果物の性質: 辞書WordStatusの単一domain model、Catalog identity基準のapplication port／use case、presentation compositionの一本化
- DB／Firebase／同期protocol変更: なし
- Drift schema version／table名／column名／asset DB変更: なし
- Firebase collection名／document ID／field名変更: なし
- `SyncDataset` stable ID／outbox payload／checkpoint変更: なし

## 1. 目的

西日辞書と日西辞書に重複しているWordStatusのdomain entity、Repository contract、watch／fetch／update use caseを`features/word_status`へ統合し、辞書方向の違いを`CatalogWordRef.catalogId`で表す。

現在はpresentation componentだけが共通化され、domain／application graphは二系統のままである。

```text
DictionaryStatusButtons(wordId, DictionaryDirection)
  -> direction switch
     -> EspJpnWordStatusViewModel
        -> WatchEspJpnWordStatusInteractor / UpdateStatusInteractor
        -> IWordStatusRepository
        -> WordStatus
     -> JpnEspWordStatusViewModel
        -> WatchJpnEspWordStatusInteractor / UpdateJpnEspStatusInteractor
        -> IJpnEspWordStatusRepository
        -> JpnEspWordStatus
```

2つのentityはfieldも意味も同じだが、Flutterの`@immutable`へ依存し、`wordId`だけではどのCatalogのstatusか識別できない。update input、use case、command、state、view model、DIも方向名を除けばほぼ同じである。このままでは、field追加、部分更新、account scope、error propagationの修正を両方へ反映し続ける必要がある。

移行後は次へ統一する。

```text
DictionaryStatusButtons(CatalogWordRef)
  -> WordStatusViewModel(CatalogWordRef)
  -> WatchWordStatus / UpdateWordStatus
  -> WordStatusRepository
  -> CatalogWordRef.catalogIdでdirection adapterを選択
     -> Esp-Jpn local/outbox adapter
     -> Jpn-Esp local/outbox adapter
```

本スライスで統合するのはdomain／application contractと、それを利用するdictionary status presentationである。方向別Drift table、DAO、local datasource、Firebase DTO／DAO／collection、sync handler、guest migration経路は変更しない。それらを`features/word_status/internal/infrastructure/{esp_jpn,jpn_esp}`へ物理集約するのは順序8で行う。

MyWordStatusは対象外とする。MyWordはCatalog wordとidentity、親子削除、同期順序、`hasNote`対応が異なるため、共通button contractだけを共有し、辞書WordStatus domainへ取り込まない。

## 2. 現行contractのcharacterization

実装前に両directionへ同じcontract suiteを適用し、次を固定する。

| 項目 | 維持するcontract |
|---|---|
| identity | `CatalogWordRef(CatalogId, positive wordId)`。同じ数値IDでもCatalogが異なれば別status |
| fields | `isLearned`、`isBookmarked`、`hasNote`、UTCの更新時刻 |
| default | 新規patch時、指定されていないfieldは`false`。既存rowの未指定fieldは維持 |
| partial update | `FieldUpdate.unchanged()`と`FieldUpdate.set(false)`を区別 |
| no-op | 3 fieldがすべてunchangedなら永続化、revision更新、outbox enqueueを行わずsuccess |
| account scope | signed-in時は実account ID、signed-out時は`guestAccountScope`を使用 |
| read isolation | 同じCatalog／word IDでもaccountが異なれば互いに見えず、上書きしない |
| direction isolation | 同じaccount／word IDでもEsp-JpnとJpn-Espは互いに見えず、上書きしない |
| watch | direction別tableの対象account／word rowだけを監視し、既存のmissing-row挙動を維持 |
| fetch | rowがない場合、対象`CatalogWordRef`の全field false statusを返す既存Esp-Jpn semanticsを共通化 |
| update error | local／outbox transaction失敗の`AppError`を同一instanceで呼出し元へ返す |
| update time | applicationで生成したUTC時刻をlocal rowとoutbox `clientUpdatedAt`に同じ値で渡す |
| signed-in update | local patchとoutbox enqueueが同一transaction。remoteへ直接writeしない |
| guest update | local patchだけを行い、outboxへenqueueしない |
| field mask | 変更fieldのみ。順序は`isLearned`、`isBookmarked`、`hasNote` |
| dataset | Esp-Jpnは`espJpnWordStatus`、Jpn-Espは`jpnEspWordStatus`のまま |
| UI state | loading、previous data、read error、toggle success／failure eventを維持 |

特に次の現行差は、統合時に暗黙に「修正」しない。

- direction別DAOの`getWordStatusAfter`／changed watchには`>=`と`>`の差がある。これは同期adapterの挙動であり順序8のcharacterization対象とする。
- watch対象rowがない場合、現Repositoryは例外を流す。fetchのdefault生成とは挙動が異なるため、本スライスではtestで現状を固定し、default streamへ変更する場合は別のbehavior changeとして扱う。
- Esp-JpnとJpn-Espで`DatabaseError.message`の文言が異なる。error type／propagationを必須contractとし、文言統一は利用箇所を確認したうえで別変更にする。
- `editAt`という既存domain名を`updatedAt`へ整理しても、DBの`editAt` column、Firebaseの`updatedAt` field、wire formatは変更しない。

## 3. 設計方針

### 3.1 単一domain modelはCatalog identityを保持する

`features/word_status/domain/word_status.dart`にFlutter非依存のimmutable modelを定義する。

```dart
final class WordStatus {
  const WordStatus({
    required this.word,
    required this.isLearned,
    required this.isBookmarked,
    required this.hasNote,
    required this.updatedAt,
  });

  final CatalogWordRef word;
  final bool isLearned;
  final bool isBookmarked;
  final bool hasNote;
  final DateTime updatedAt;
}
```

決定事項:

- raw `int wordId`だけをdomain identityにしない。
- direction専用subclass、generic type parameter、`bool isJpnEsp`を追加しない。
- `CatalogWordRef`のassertに加え、外部入力のpositive ID validationは既存route／Catalog boundaryで維持する。
- `updatedAt`は常にUTCとして生成／mappingする。timezone変換をmapperへ分散させない。
- `package:flutter/material.dart`の`@immutable`をdomainから除去する。必要なら`meta` annotationではなくDartのfinal field／final classで不変性を表す。
- equality追加は既存contractではないため、testが必要な場合もfield比較helperで開始し、このスライスへ値オブジェクト化を混ぜない。

旧`WordStatus`と`JpnEspWordStatus`をtypedefで長期温存しない。consumer切替中だけdeprecated compatibility exportが必要なら、stage内で追加・撤去し、完了時には単一classだけを残す。

### 3.2 application portは画面操作に必要な最小contractにする

`features/word_status/application/port/word_status_repository.dart`は次の責務だけを公開する。

```dart
abstract interface class WordStatusRepository {
  Future<Result<WordStatus?>> get(
    CatalogWordRef word, {
    required String accountId,
  });

  Stream<WordStatus> watch(
    CatalogWordRef word, {
    required String accountId,
  });

  Future<Result<WordStatus>> update(
    CatalogWordRef word, {
    required FieldUpdate<bool> isLearned,
    required FieldUpdate<bool> isBookmarked,
    required FieldUpdate<bool> hasNote,
    required DateTime updatedAt,
    required String? accountId,
  });
}
```

現行Repository interfaceにある次のAPIは共通application portへ移さない。

- `watchLocalChangedIds`
- `getLocalWordStatusAfter`
- `getLocalWordStatusById`
- `deleteWordStatus`
- remote apply／acknowledge用操作

これらは画面applicationのRepository責務ではない。未使用APIは削除し、sync／guest migrationが必要とするraw local操作は順序8まで既存direction別local datasource contractに残す。画面用portと同期用portを一つへ統合しない。

### 3.3 direction選択は一か所のRepository adapterへ閉じ込める

共通use caseやpresentationで`switch (catalogId)`を繰り返さない。application portの実装は`CatalogId`ごとに登録されたdirection adapterを選択する。

```text
WordStatusRepository
  -> CatalogWordRef.catalogId
     -> espJpn adapter -> existing Esp-Jpn local datasource + OutboxWriter
     -> jpnEsp adapter -> existing Jpn-Esp local datasource + OutboxWriter
```

移行中の内部contract例:

```dart
abstract interface class DictionaryWordStatusAdapter {
  CatalogId get catalogId;
  Future<Result<WordStatus?>> get(...);
  Stream<WordStatus> watch(...);
  Future<Result<WordStatus>> update(...);
}
```

- adapterは受け取った`CatalogWordRef.catalogId`が自身のCatalogと一致することをassert／testする。
- direction→`SyncDataset`の対応はadapter内部に残し、domain／application use caseへ公開しない。
- local rowからdomainへのmapperは必ずadapter側で`CatalogWordRef`を補う。
- adapter registryはduplicate `CatalogId`とmissing `CatalogId`を構築時に検出する。現在の`CatalogId.values`をすべて実装していることをtestする。
- `switch`で直接2具象型を保持する実装でもよいが、fallbackでEsp-Jpnを選ぶ実装は禁止する。
- 既存の方向別Repository実装をこのadapterへ変更する段階では、SQL、transaction範囲、outbox payloadを変えない。

順序7完了時に方向別adapterが旧feature directoryへ残ることは暫定的に許容する。順序8で`features/word_status/internal/infrastructure/{esp_jpn,jpn_esp}`へ移し、local／remote／syncの物理ownershipを完成させる。

### 3.4 watch／fetch／update use caseを一本化する

`features/word_status/application`に次を置く。

- `WatchWordStatus`: `CatalogWordRef`を受け、CurrentSessionからaccount scopeを解決してstreamを返す。
- `FetchWordStatus`: `CatalogWordRef`を受け、rowがなければ全field falseのdefault domain modelを返す。
- `UpdateWordStatus`: `UpdateWordStatusCommand`を受け、no-op判定、UTC timestamp生成、CurrentSession解決、Repository update、error propagationを一度だけ実装する。

command例:

```dart
final class UpdateWordStatusCommand {
  const UpdateWordStatusCommand({
    required this.word,
    this.isLearned = const FieldUpdate.unchanged(),
    this.isBookmarked = const FieldUpdate.unchanged(),
    this.hasNote = const FieldUpdate.unchanged(),
  });

  final CatalogWordRef word;
  final FieldUpdate<bool> isLearned;
  final FieldUpdate<bool> isBookmarked;
  final FieldUpdate<bool> hasNote;
}
```

- `DictionaryDirection`からCatalogへの変換をuse case内に置かない。
- no-opはRepositoryを呼ばず`Result.success(null)`を返す。
- clockを注入可能にする場合はdefaultを`DateTime.now`とし、生成値を即UTC化する。production behaviorは変えない。
- applicationからRiverpod、Flutter、Drift、Firebase、`SyncDataset`をimportしない。
- `FetchEspJpnWordStatusUsecase`はproduction consumerがないことを再確認し、共通`FetchWordStatus`のcontract testへ移管後に削除する。不要ならDI provider自体を作らない。

### 3.5 presentation state／command／view modelも共通application contractへ接続する

現在の`WordStatusState`／`JpnEspWordStatusState`、2つのcommand、2つのview modelを各一つへ統合する。

```text
WordStatusState(QueryState<WordStatus>)
WordStatusCommand(CatalogWordRef, UpdateWordStatus)
DictionaryWordStatusViewModel(WordStatusState, WordStatusCommand)
```

`DictionaryStatusButtons`の公開入力は次へ変更する。

```dart
DictionaryStatusButtons(word: CatalogWordRef(...))
```

- `wordId + DictionaryDirection`の組を公開しない。
- provider family keyも`CatalogWordRef`にし、同じ数値IDの異なるCatalogが同じprovider instanceを共有しないことをtestする。
- `QueryState.loading(previousData: ...)`とfailure時previous data保持を維持する。
- toggleは現在表示しているbool値を反転した`FieldUpdate.set`を送る。
- success／failure eventの型とUI通知挙動を維持する。event名の整理は可能だが、二方向のclassを残さない。
- MyWord用adapterは現状どおり別view modelを共通button UIへ渡す。MyWordの`hasNote=false`／no-op挙動を変更しない。

`DictionaryDirection`は辞書WordStatus以外の有効consumerがないことを確認し、すべて`CatalogWordRef`へ切り替わったら削除する。Catalog identityからpresentation都合のdirection enumへ戻す変換は追加しない。

### 3.6 DIをdomain identity基準へ一本化する

目標provider graphは次とする。

```text
wordStatusRepositoryProvider
  -> Esp-Jpn DictionaryWordStatusAdapter
  -> Jpn-Esp DictionaryWordStatusAdapter

watchWordStatusProvider(CatalogWordRef)
updateWordStatusUseCaseProvider
wordStatusCommandProvider(CatalogWordRef)
wordStatusUiStateProvider(CatalogWordRef)
dictionaryWordStatusViewModelProvider(CatalogWordRef)
```

- app-level `DictionaryStatusButtons`はdirection別DIをimportしない。
- Search、Ranking、Quiz、WordPageは共通provider／widgetだけを利用する。
- legacy direction DIには順序8で必要なlocal datasource、remote datasource、sync handler providerだけを残す。
- `sync_composition.dart`と`guest_migration_composition.dart`は本スライスでは既存direction infra providerを利用し続ける。
- providerの`read`／`watch` semanticsを不用意に変更せず、session変更時に新account scopeへ再接続される現行挙動をwidget／provider testで確認する。

### 3.7 DB／Firebase／Sync境界は触らない

本スライスでは次を不変とする。

| 境界 | Esp-Jpn | Jpn-Esp |
|---|---|---|
| Drift table | `esp_jpn_word_status` | `jpn_esp_word_status` |
| Drift DAO／datasource | 既存型を維持 | 既存型を維持 |
| Firebase collection | `WordStatus` | `JpnEspWordStatus` |
| SyncDataset | `espJpnWordStatus` | `jpnEspWordStatus` |
| entity ID | decimal `wordId` string | decimal `wordId` string |
| checkpoint／queue | 既存datasetごと | 既存datasetごと |
| sync handler | 既存handler | 既存handler |

domain entityの統合を理由にFirebase DTOを共通化しない。Firebase DTOが旧domain entityへ変換するmethodは、remote syncで未使用なら削除し、必要なら共有domainではなくdirection adapter向けDTOのままにする。remote payloadとcollection schemaをdomain class名へ追従させない。

## 4. 実施手順

### Stage 0: preflightと利用箇所の固定

1. 順序6のCatalog、WordDetail、Search、Quiz、Ranking、DB regressionが成功していることを確認する。
2. 旧domain entity、Repository interface、use case、direction provider、`DictionaryDirection`の全importerを`rg`で一覧化する。
3. productionで未使用の`FetchEspJpnWordStatusUsecase`、Repositoryのdelete／local sync helperをtest-only利用と区別する。
4. `status_update_contract_test`、`status_account_scope_test`、outbox testを両directionのcharacterization suiteとして整理する。
5. watch missing-row、session切替、UI previous data、toggle eventの現行挙動をtestで固定する。
6. table／collection／dataset／payload／field maskのsnapshotを記録する。

### Stage 1: 共通domain modelとapplication portをadditiveに追加する

1. `features/word_status/domain/word_status.dart`に`CatalogWordRef`を持つ単一modelを追加する。
2. UTC timestamp、copy semantics、Catalog identity保持をunit testする。
3. `application/port/word_status_repository.dart`へget／watch／updateの最小contractを追加する。
4. `UpdateWordStatusCommand`とno-op判定を追加する。
5. domain／application import boundary testを追加し、Flutter／Riverpod／Drift／Firebase／SyncDataset依存が0件であることを確認する。

### Stage 2: 方向別Repositoryを共通domainへのadapterにする

1. Esp-Jpn local row mapperが`CatalogId.espJpnMain`の`CatalogWordRef`を生成するよう変更する。
2. Jpn-Esp local row mapperが`CatalogId.jpnEspMain`の`CatalogWordRef`を生成するよう変更する。
3. 方向別Repository実装の戻り値を共通`WordStatus`へ切り替える。
4. 各adapterが誤ったCatalogを受けた場合に別tableへ書かないことをtestする。
5. 共通Repository adapter／registryを追加し、全`CatalogId`が一意に登録されることをtestする。
6. local transaction、outbox dataset、entity ID、payload、field mask、revision、timestampが移行前と同一であることを既存testで確認する。
7. sync handler／guest migrationが利用するdirection別local datasource interfaceは変更しない。

### Stage 3: 共通use caseへ切り替える

1. `WatchWordStatus`を実装し、CurrentSessionからaccount／guest scopeを一度だけ解決する。
2. `FetchWordStatus`を実装し、missing rowを対象`CatalogWordRef`のdefault statusへ変換する。
3. `UpdateWordStatus`を実装し、部分更新、no-op、UTC timestamp、error propagationを統合する。
4. 旧Esp-Jpn／Jpn-Esp use case contract testを共通suiteへ移す。
5. 同じuse case instanceに両Catalogのcommandを渡し、正しいadapterだけが呼ばれることをtestする。
6. legacy use case providerを新use caseへ委譲する短い移行期間を設ける。consumer切替後に委譲providerも削除する。

### Stage 4: presentation modelとproviderを統合する

1. 共通`WordStatusState`を新domain modelへ切り替える。
2. `WordStatusCommand`を`CatalogWordRef`と共通update use case入力へ切り替える。
3. direction別view modelを単一`DictionaryWordStatusViewModel`へ統合する。
4. provider family keyを`CatalogWordRef`へ変更する。
5. app-level `DictionaryStatusButtons`からdirection switchと旧DI importを除去する。
6. `DictionaryStatusButtons`の引数を`word`だけにし、内部で共通view model providerをwatchする。
7. loading、previous data、read error、toggle success／failureをprovider／widget testで確認する。

### Stage 5: 全consumerをCatalogWordRef入力へ変更する

1. WordPageはroute／load keyが保持する`CatalogWordRef`をそのままstatus buttonへ渡す。
2. Search resultはdirection enumを再生成せず、resultが保持するCatalog identityから`CatalogWordRef`を渡す。
3. Ranking projectionはEsp-Jpn固定という暗黙値を呼出し側に散らさず、projection／adapter境界で`CatalogWordRef`を構築する。
4. Quiz gameは既存のEsp-Jpn `CatalogWordRef`をstatus buttonへ渡す。
5. copy／legacy widgetを含む全`DictionaryStatusButtons`呼出しを更新する。
6. widget testのoverride keyをraw intから`CatalogWordRef`へ更新する。
7. 同一word IDのEsp-Jpn／Jpn-Esp buttonを同じProviderScopeに置き、stateが混在しないことをtestする。

### Stage 6: 旧domain／application／presentation graphを削除する

1. `esp_word_status.dart`と`jpn_esp_word_status.dart`を削除する。
2. `IWordStatusRepository`と`IJpnEspWordStatusRepository`を削除する。
3. 方向別fetch／watch／update use caseとinput dataを削除する。
4. `EspJpnWordStatusCommand`／`JpnEspWordStatusCommand`、方向別state／view modelを削除する。
5. direction別DIからapplication／presentation providerを削除し、順序8に必要なinfra／sync providerだけを残す。
6. `DictionaryDirection`のconsumerが0件ならenum fileを削除する。
7. Firebase DTO／mapperに旧domain conversion methodが残る場合は、同期wire mappingに不要なmethodだけを削除する。DTO／collection定数自体は残す。
8. 旧symbol、旧path、raw direction switchの参照が0件であることを確認する。

### Stage 7: regressionと引き継ぎ確認

1. 共通domain／application／presentation testを実行する。
2. 両directionのlocal patch、account scope、outbox enqueue contract testを実行する。
3. WordPage、Search、Ranking、Quizのwidget／view model testを実行する。
4. sync handler、SyncEngine registry、guest migration testを実行し、方向別infra経路が維持されることを確認する。
5. DB schema／migration／Web seeder testを実行する。
6. Firebase emulator／mapper contract testがある場合はcollection／field不変を確認する。
7. `flutter analyze`、format check、boundary検査、`git diff --check`を実行する。

## 7. リスクと対策

### 同じ数値word IDのstatusが方向を跨いで混在する

domain、command、provider family keyをすべて`CatalogWordRef`基準にする。raw `int`を受けるのはdirection adapterからDAOへ渡す直前だけに限定し、同一ProviderScopeに同じIDの両Catalogを置くtestを追加する。

### domain統合と同時に同期datasetまで一つにしてしまう

共通application portから`SyncDataset`を見せず、dataset選択はdirection adapter／既存sync handlerへ残す。queue、checkpoint、remote collectionの2系統を完了条件として明示する。

### 旧Repositoryの同期専用APIを共通portへ持ち込む

production importerを先に棚卸しし、画面用get／watch／updateだけを共通portにする。guest migrationとsync handlerは既存local datasource contractを利用し続け、順序8で専用portとして整理する。

### watchのmissing-row挙動がfetchと一緒に変わる

fetch defaultとwatch errorを別contract testにする。本スライスでは統合を目的とし、missing rowを自動insertする、streamでdefaultを流すなどの仕様変更を混ぜない。

### session変更後も旧accountのstreamを購読する

CurrentSessionをwatchするprovider graphとprovider familyのdispose／再生成をtestする。repositoryへaccount IDを隠れたglobalとして持たせず、use caseから明示的に渡す。

### direction別DIを一度に削除してsync／guest migrationが壊れる

方向別DIをapplication／presentationとinfra／syncに分類する。前者だけを削除し、`sync_composition.dart`と`guest_migration_composition.dart`のproviderは順序8まで維持する。

### `editAt` renameがDB／Firebase renameへ波及する

domainでは`updatedAt`を使用しても、mapperで既存`editAt` column／`updatedAt` fieldへ変換する。schema／wire snapshotを検証し、generated codeを変更対象にしない。

### MyWordStatusまで共通modelへ取り込む

辞書statusの公開型は`CatalogWordRef`を必須にし、String UUIDのMyWordを表現できない設計にする。MyWordは共通buttonの小さなpresentation interfaceだけを利用し続ける。

### 一時compatibility aliasが恒久化する

alias／委譲providerを追加する場合はconsumer一覧と削除stageを同じ変更セットに含める。完了検査で旧symbolを0件にし、deprecated fileを残さない。
