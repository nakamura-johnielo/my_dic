# 移行順序5: `hasConj`をWordDetail Routeから除去する

- 状態: 実施前
- 対象: [`concept.md`](./concept.md) の「移行順」5
- 前提: [`4.plan.md`](./4.plan.md) のQuiz→Search依存除去が実装・検証済み
- 成果物の性質: WordDetail identity／Catalog read境界／route codecの切替
- DB／Firebase／同期protocol変更: なし
- route path変更: なし
- route query変更: 新規URLは`catalog`のみを出力し、旧`type`／`hasConj`は互換入力としてのみ扱う

## 1. 目的

WordDetailへの遷移入力を、呼び出し側が申告する`wordId / wordType / hasConj`から、Catalog-owned identityである`CatalogWordRef`だけへ変更する。活用の有無をURL、Search結果、Ranking projection、Quiz画面の申告値で決めず、WordDetail取得時にCatalogの`ConjugationReader`が再判定する。

現在は次の経路で`hasConj`が画面内部まで伝播している。

```text
Search / Ranking / Quiz
  -> WordDetailRoute(wordId, wordType, hasConj)
  -> WordPageLoadKey(wordId, wordType, hasConj)
  -> WordDetailQuery(wordId, wordType, hasConjugation)
  -> if (hasConjugation) legacy Conjugation Repositoryを読む
  -> if (route.hasConj) Conjugacion tabとQuiz buttonを表示する
```

この構造では、同じCatalog wordに対して`hasConj=true`と`false`の2種類のURLとprovider keyが成立する。古いbookmark、手書きdeep link、Search／Rankingのstale projectionが誤った値を渡すと、実データがあっても取得されない、または存在しない活用tabが表示される。

移行後は次の経路に統一する。

```text
Search / Ranking / Quiz
  -> WordDetailRoute(CatalogWordRef)
  -> WordPageLoadKey(CatalogWordRef)
  -> WordDetailQuery(CatalogWordRef)
  -> CatalogReader.getEntryDetail(word)
  -> EspJpnの場合だけConjugationReader.getConjugation(word)
  -> 実際の取得結果からConjugacion tabとQuiz buttonを表示する
```

このスライスではroute parameterを減らすだけでなく、WordDetail applicationとpresentationをCatalog公開DTOへ切り替える。legacy Repositoryやlegacy entityのままでは、routeから`hasConj`を消してもCatalogが能力の正本にならず、移行順序6の物理移動を開始できないためである。

## 2. 現行contractのcharacterization

実装前に次の挙動をtestで固定する。

| 項目 | 現行の意味／移行時の扱い |
|---|---|
| route path | `word/:wordId`を維持する |
| word ID | positive integer。0以下、欠落、非数値はinvalid route |
| direction | 現在は`type=WordType.name`。新規URLでは`catalog=CatalogId.wireValue`へ置換 |
| Esp→Jpn primary read | dictionary失敗はquery全体のfailure |
| Jpn→Esp primary read | dictionary失敗はquery全体のfailure |
| conjugation read失敗 | Esp→Jpn dictionaryを成功として残し、source=`conjugation`のwarningを返す |
| conjugationなし | 成功かつconjugationなし。活用tab／Quiz buttonを表示しない |
| 空dictionary | `QueryState.empty` |
| stale response | provider破棄後または世代更新後のresponseを反映しない |
| initialization | provider instanceごとに一度だけ実行 |
| status button | Catalogに対応する既存`DictionaryDirection`へpresentation境界で変換 |
| Quiz遷移 | Esp→Jpnかつ実際のconjugation dataがある場合だけ有効 |
| Search highlight | 現在のSearch queryを活用表内で強調する挙動は維持する |

旧URLについては、少なくとも次をroute contract testでcharacterizeする。

```text
/word/42?type=espJpn&hasConj=true
/word/42?type=espJpn&hasConj=false
/word/42?type=jpnEsp&hasConj=false
```

`hasConj`の値が異なっても、同じ`CatalogWordRef`へparseされなければならない。`hasConj`が欠落、未知値、任意文字列の場合も、identityが有効ならroute parseの成否に影響させない。

## 3. 設計方針

### 3.1 Routeは`CatalogWordRef`だけを公開する

公開contractを次の形へ変更する。

```dart
final class WordDetailRoute {
  const WordDetailRoute({required this.word});

  static const path = 'word/:wordId';

  final CatalogWordRef word;

  Map<String, String> get pathParameters => {
    'wordId': '${word.wordId}',
  };

  Map<String, String> get queryParameters => {
    'catalog': word.catalogId.wireValue,
  };
}
```

決定事項:

- pathは変えず、既存router treeとroute nameを維持する。
- 新規serializationは`CatalogId.name`ではなくstableな`wireValue`を使う。
- `hasConj` field、query parameter定数、validation、serializationを削除する。
- `WordType`を公開route fieldとして残さない。
- `toString()`やenum `.name`をwire formatとして使わない。
- route constructorはtypedな`CatalogWordRef`だけを受け、raw `wordId`とdirectionの組み合わせを各consumerへ再公開しない。

新規URLの例:

```text
/word/42?catalog=esp-jpn-main
/word/42?catalog=jpn-esp-main
```

### 3.2 旧deep linkはparse時だけ互換対応する

route parserは次の優先順位でCatalogを決める。

1. `catalog`がある場合は`CatalogId.tryParse`で解決する。
2. `catalog`がなく旧`type`がある場合だけ、app routing内のprivate legacy mapperで`espJpn -> espJpnMain`、`jpnEsp -> jpnEspMain`へ変換する。
3. `catalog`も解決可能な旧`type`もなければinvalid routeとする。
4. `catalog`と`type`が両方あり、両方が有効で同じCatalogを表す場合は受理する。
5. `catalog`と`type`が両方有効だが競合する場合はinvalid routeとする。

`hasConj`は互換parserでも読まない。query mapに残っていても無視し、値が`true`、`false`、不正文字列、欠落のどれでもCatalog能力の判定に使わない。これにより旧bookmarkを壊さず、誤った値を信頼する経路だけを除去する。

旧`type` fallbackは入力互換に限定する。`queryParameters` getterと全production callerは`catalog`だけを生成する。fallback削除はdeep linkのsupport windowを別途決めてから行い、本スライスでは既存URLを一斉に無効化しない。

### 3.3 WordDetail queryとprovider keyも`CatalogWordRef`へ統一する

`WordDetailQuery`と`WordPageLoadKey`は次だけを保持する。

```dart
final class WordDetailQuery {
  const WordDetailQuery({required this.word});
  final CatalogWordRef word;
}

@immutable
final class WordPageLoadKey {
  const WordPageLoadKey(this.word);
  final CatalogWordRef word;

  // equality/hashCodeはCatalogWordRefへ委譲
}
```

- `hasConjugation`／`hasConj`を削除する。
- `wordId`／`wordType`の平行fieldを持たない。
- 同じCatalog wordのprovider family keyを一つにする。
- presentationが必要なraw IDは`word.wordId`でのみunwrapする。
- Catalog方向による表示分岐は`word.catalogId`または取得済みsealed detailの型で行う。

### 3.4 WordDetail applicationはCatalog公開portだけを読む

`LoadWordDetailQuery`の依存を次へ置換する。

```dart
LoadWordDetailQuery(
  CatalogReader catalogReader,
  ConjugationReader conjugationReader,
)
```

処理順は次のとおりとする。

1. `CatalogReader.getEntryDetail(query.word)`を呼ぶ。
2. primary readが失敗した場合は同じ`AppError`をquery failureとして返す。
3. `JpnEspEntryDetail`なら、`JpnEspWordDetailViewData`へmapして成功を返す。Conjugation readerは呼ばない。
4. `EspJpnEntryDetail`なら、同じ`CatalogWordRef`で`ConjugationReader.getConjugation`を呼ぶ。
5. conjugationが非nullならdetailへ含める。
6. conjugationがnullなら活用なしとして、issueなしのdetailを返す。
7. conjugation readが失敗した場合はdictionary detailを残し、`QueryIssue(source: 'conjugation', error: error)`を返す。

この取得では`hasConjugation()`を先に呼ばない。WordDetailは最終的に活用データ自体を必要とするため、存在確認後に再取得するとDB readが二重になり、確認と取得の間に結果がずれる余地も増える。`getConjugation()`の`Result<CatalogConjugation?>`を、存在確認と取得を兼ねる正本とする。

`ConjugationReader.hasConjugation`はSearch／Ranking等の軽量projection向けCatalog能力として削除しない。ただしWordDetailの業務実行可否には使用しない。

### 3.5 WordDetailの表示modelをCatalog DTOへ切り替える

`WordDetailViewData`はlegacy core entityを保持せず、Catalog公開DTOを保持する。

```dart
sealed class WordDetailViewData {
  const WordDetailViewData(this.word);
  final CatalogWordRef word;
}

final class EspJpnWordDetailViewData extends WordDetailViewData {
  final List<EspJpnEntry> entries;
  final CatalogConjugation? conjugation;
}

final class JpnEspWordDetailViewData extends WordDetailViewData {
  final List<JpnEspEntry> entries;
}
```

- Listはunmodifiableを維持する。
- `EspJpnDictionary`、`JpnEspDictionary`、`EspConjugacions`をfieldに残さない。
- `CatalogEntryDetail`から画面用variantへのmappingはWordDetail application内のpure mapperまたは`LoadWordDetailQuery`内で行う。
- 不可能な組み合わせ、例えばEsp→Jpn refに対してJpn→Esp detailが返った場合は、silent castや空表示にせずtypedな`BusinessRuleError`へ変換する。
- Catalog readerから返った`detail.word`がrequest identityと異なる場合もcontract violationとしてfailureにする。

dictionary fragmentとconjugation componentはCatalog DTOを直接表示できるように変更する。活用表の日本語label、mood／tenseの表示順、subject順、検索語highlightは現行UIを維持し、`CatalogMoodTense`／`CatalogSubject`から表示文字列への変換はWordDetail presentation-owned helperに置く。Catalog enumへUI文言getterを追加しない。

### 3.6 UIはRoute hintではなく取得結果で能力を表示する

`WordPageFragment`は次の規則で組み立てる。

- loading／failure／empty時にどちらのdictionary fragmentを置くかは`route.word.catalogId`で決める。
- status buttonは`CatalogId.espJpnMain -> DictionaryDirection.espJpn`、`CatalogId.jpnEspMain -> DictionaryDirection.jpnEsp`へpresentation境界で変換する。
- loaded時はsealed `WordDetailViewData`のvariantを表示する。
- Conjugacion tabとQuiz floating buttonは、`EspJpnWordDetailViewData.conjugation != null`のときだけ作る。
- conjugation取得失敗時はdictionaryを表示し、既存と同じwarningをdictionary側で表示する。誤った空の活用tabは作らない。
- conjugationなしは通常のdictionary-only画面であり、warningにしない。

route hintがなくなるため、活用tabはCatalog read成功後に初めて追加される。`_TabWordPageState.didUpdateWidget`のtab数変更処理が、1 tabから2 tabsへの更新を安全に扱うことをwidget testで固定する。

Quiz buttonの有効性は取得済みconjugationとdictionary headwordの両方から決める。Quiz実行route自体は既存`QuizGameRoute`のままとし、このスライスでserializationを変更しない。

### 3.7 全navigation callerをtyped routeへ切り替える

callerごとの変換は次のとおりである。

| caller | `CatalogWordRef`の構築 | `hasConjugation`の残る用途 |
|---|---|---|
| Jpn→Esp Search item | `CatalogId.jpnEspMain × item.wordId` | routeには使わない |
| Esp→Jpn Search item | `CatalogId.espJpnMain × item.wordId` | Search cardのQuiz action表示には利用可 |
| conjugation suggestion | `CatalogId.espJpnMain × item.wordId` | routeには使わない |
| Ranking item | `CatalogId.espJpnMain × ranking.wordId` | Ranking card内の能力表示には利用可 |
| Quiz game dictionary link | `CatalogId.espJpnMain × input.wordId` | routeには使わない |

Search／Rankingの`hasConjugation` projectionは、このスライスでは削除しない。一覧UIが能力iconやQuiz actionを事前表示する用途は許容する。ただしWordDetail route、provider key、query、applicationの正当性判定へ渡してはならない。

callerが`CatalogId`を暗黙のdefaultで決めるhelperは作らない。各callerが持つ検索方向／画面contractから明示的に構築し、将来別Catalogが追加された際に誤配送をcompile／testで発見できるようにする。

### 3.8 DIはCatalog compositionを利用する

`wordPageViewModelProvider`はlegacy repository providerを直接読まず、app compositionで公開済みの`catalogReaderProvider`と`conjugationReaderProvider`を読む。

```text
wordPageViewModelProvider(word)
  -> LoadWordDetailQuery(CatalogReader, ConjugationReader)
  -> catalogReaderProvider / conjugationReaderProvider
  -> legacy adapters
  -> existing repositories and DB
```

- WordDetail application／presentationから`core/domain/i_repository/**` importを削除する。
- provider overrideでfake `ILoadWordDetailQuery`またはCatalog portを注入できる現行testabilityを維持する。
- 新しいRepository instanceやdatabase graphをWordDetail DI内で構築しない。
- Catalog adapterの具象型をWordDetailから参照しない。

## 7. リスクと対策

### 旧deep linkを一斉に壊す

pathを維持し、旧`type`からCatalog IDへ変換するparse-only fallbackを置く。旧`hasConj`は能力値として読まず、任意値でもidentityが有効なら受理する。新serializerが旧parameterを再生成しないことをtestする。

### 新旧direction parameterが競合する

`catalog`を無条件優先して曖昧なURLを受理せず、両方が有効で競合する場合はinvalid routeにする。同じ意味なら互換URLとして受理する。

### 存在確認と活用取得でDBを二重に読む

WordDetailでは`getConjugation`のnullable resultを能力判定とデータ取得に兼用する。`hasConjugation`を事前呼び出ししないことをmock call countでtestする。

### conjugation失敗でdictionaryまで消える

primary Catalog detailとoptional conjugationを別error boundaryに置く。conjugation failureは`QueryIssue`へ変換し、dictionary dataとidentityを維持する。

### route hint削除後に誤ったtabが残る

tab作成条件を取得済み`CatalogConjugation`の非nullだけに限定する。nullとfailureでtabがないこと、successでloading後にtabが追加されることをwidget testする。

### 1 tabから2 tabsへの更新でTabControllerが不整合になる

既存`didUpdateWidget`のcontroller再作成をcharacterization testで固定する。active index clamp、controller dispose、TabBar／TabBarViewのlength一致を確認する。

### Catalog DTOへの切替で表示が欠落する

dictionary headword、HTML content、examples、idioms、supplements、活用label、subject順、participlesをfixtureで比較する。現行画面が表示していないfieldを新UIへ追加せず、表示差分を最小化する。

### presentationのためにCatalog modelへUI getterを追加する

日本語labelやWidget向け変換はWordDetail presentation helperへ置く。Catalog公開enum／DTOはFlutterとlocale文言をimportしない。

### Search／Rankingのcapability projectionまで同時に削除する

一覧でQuiz actionやiconを表示する用途は維持する。今回除去するのはその値をWordDetailのidentity／業務判断として渡す経路だけとする。

### WordStatus統合まで巻き込む

status button直前でCatalog IDを既存`DictionaryDirection`へ変換し、方向別WordStatus contractは維持する。status identity統合は移行順序7へ残す。

## 10. 次の移行への引き継ぎ

移行順序6では、legacy coreに残るWord／Dictionary／Conjugation entity、Repository、datasource、DAO、mapperをCatalog配下へ移す。本スライス完了後、WordDetailはCatalog公開port／DTOだけを参照するため、物理移動によるconsumer差分をCatalog legacy adapterとcomposition内へ閉じ込められる。
