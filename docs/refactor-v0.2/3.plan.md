# 移行順序3: Catalog公開portとlegacy Repository adapterを実装する

- 状態: 実施前
- 対象: [`concept.md`](./concept.md) の「移行順」3
- 前提: [`2.plan.md`](./2.plan.md) のidentity contractが実装・検証済み
- 成果物の性質: additiveなCatalog read seamの追加
- DB／Firebase／同期protocol変更: なし

## 1. 目的

Search、WordDetail、Quiz、Ranking、WordStatusがCatalog内部entityや方向別legacy Repositoryを直接参照しなくて済むように、Catalog-ownedの公開read contractを作る。そのcontractを現行の`IEsjDictionaryRepository`、`IJpnEspDictionaryRepository`、`IConjugacionsRepository`へ接続するanti-corruption adapterを追加する。

このスライスは新しいseamを実動可能にするところまでを対象とし、既存consumerの一括切替は行わない。adapter contract testとcomposition testで新経路を完成させた後、Quiz依存除去、route変更、WordDetail移行などを個別スライスで行う。

## 2. 設計方針

### 2.1 公開portはconsumer非依存

```text
lib/features/catalog/
├── port/
│   ├── catalog_id.dart
│   ├── catalog_word_ref.dart
│   ├── catalog_reader.dart
│   ├── conjugation_reader.dart
│   └── model/
│       ├── catalog_entry_detail.dart
│       ├── esp_jpn_entry.dart
│       ├── jpn_esp_entry.dart
│       └── catalog_conjugation.dart
└── internal/
    └── infrastructure/
        └── legacy/
            ├── legacy_catalog_reader_adapter.dart
            ├── legacy_conjugation_reader_adapter.dart
            └── legacy_catalog_mapper.dart
```

公開port／modelは次をimportしない。

- `core/domain/entity/**`
- `core/domain/i_repository/**`
- Drift／DAO／Firebase型
- Search、WordDetail、Quiz、Ranking、WordStatusの型
- Flutter／Riverpod

`core/shared/utils/result.dart`と、Catalog public identity同士への依存だけを許可する。errorの共通表現をこのスライスで再設計せず、既存`Result`／`AppError`を保つためである。

### 2.2 readerの責務を分ける

初期contractは次の責務に限定する。method名・DTO field名は実装開始時のcontract testで確定し、同じ意味のmethodを増やさない。

```dart
abstract interface class CatalogReader {
  Future<Result<CatalogEntryDetail>> getEntryDetail(CatalogWordRef word);
}

abstract interface class ConjugationReader {
  Future<Result<CatalogConjugation?>> getConjugation(CatalogWordRef word);
  Future<Result<bool>> hasConjugation(CatalogWordRef word);
}
```

- `CatalogReader`はdictionary detailを返し、conjugationを自動的に合成しない。
- `ConjugationReader`はCatalogの活用能力だけを公開する。
- dictionary成功＋conjugation失敗を部分成功として扱う判断はWordDetail application queryの責務に残す。
- word search、pagination、ranking enrichment、Quiz candidate selectionはこの汎用readerへ追加しない。それぞれSearch queryまたはQuiz-owned portの責務である。
- write methodは一切持たない。

### 2.3 公開DTOはlegacy entityを漏らさない

`CatalogEntryDetail`はCatalog variantを型で表現するsealed contractとする。

```dart
sealed class CatalogEntryDetail {
  const CatalogEntryDetail(this.word);
  final CatalogWordRef word;
}

final class EspJpnEntryDetail extends CatalogEntryDetail { ... }
final class JpnEspEntryDetail extends CatalogEntryDetail { ... }
```

方向差を巨大なnullable DTOへ押し込めず、次をvariant別のimmutable DTOへ写す。

- Esp→Jpn: dictionary ID、word、headword、content、origin、examples、idioms、supplements
- Jpn→Esp: dictionary ID、word ID、word、headword、content、examples
- conjugation: word ref、mood／tense／subjectごとの活用、participles

公開DTOはList／Mapをunmodifiableにし、legacy entity instanceをfieldとして保持しない。既存の`MoodTense`、`Subject`、`PartOfSpeech`などCatalog-ownedになる予定のenumを一時的に公開DTOが直接参照する場合は、移行順序6でCatalog配下へ移動する対象として明記する。consumer／presentation固有型は参照しない。

全nested modelを一度に複製するコストが高い場合でも、`Object`、`dynamic`、HTMLだけへの不可逆な平坦化、legacy entityのwrapperで境界を迂回しない。必要なfieldをcontract testから逆算し、Catalog-owned DTOとして明示する。

### 2.4 unsupported能力とerror semantics

| 呼び出し | 結果 |
|---|---|
| Esp→Jpn detail | legacy Esp→Jpn Repositoryを呼び、DTOへmap |
| Jpn→Esp detail | legacy Jpn→Esp Repositoryを呼び、DTOへmap |
| Esp→Jpn conjugation | legacy Conjugation Repositoryを呼び、DTOへmap |
| Jpn→Esp conjugation／has | DBへ誤問い合わせせず、明示的なunsupported `BusinessRuleError` |
| legacy Repository failure | 同じ`AppError` instanceを`Result.failure`で伝播 |
| empty／not found | legacy Repositoryの現在の意味を維持し、このスライスで方向間の差を変更しない |

Jpn→Espの活用を単に`null`／`false`で返すと「対応しているがデータがない」と「Catalogに能力がない」を区別できないため、unsupported errorとする。画面表示用の静的な能力判定が必要になった場合は、移行順序5で`CatalogCapabilities`の追加を検討し、`CatalogId`へUI都合のbooleanを埋め込まない。

### 2.5 adapterとcompositionの依存方向

```text
consumer  ───────> Catalog port
                       ^
                       |
app/bootstrap ──> legacy adapter ──> existing core Repository ports
```

- adapter classは`catalog/internal/infrastructure/legacy`に置く。
- adapterだけが新Catalog DTOとlegacy core entityの双方を知る。
- 既存Repository実装、DAO、converterは変更しない。
- app composition rootがlegacy Repository providerからadapterを構築し、`CatalogReader`／`ConjugationReader`として公開する。
- Catalog portはadapterやDIをexportしない。

## 3. 実施手順

### Stage 0: preflightとcontract inventory

1. 移行順序2のidentity testと全体analyzeが成功していることを確認する。
2. 現行dictionary／conjugation entityの全fieldとnullabilityを棚卸しする。
3. WordDetailが実際に表示するfieldを確認し、DTO mappingで情報を失わないことをtest fixtureに落とす。
4. 既存Repositoryのfailure／empty semanticsをcharacterization testで固定する。

### Stage 1: 公開DTOを追加

1. sealed `CatalogEntryDetail`と方向別variantを追加する。
2. nested example／idiom／supplement／conjugation modelをimmutable public DTOとして追加する。
3. List／Mapのdefensive copyとvalue semanticsの要否をcontract testで固定する。少なくとも外部からmutable collectionを変更できないことを保証する。
4. DTOにstatus、ranking、pagination、route、Quiz fieldが混入していないことをレビューする。

### Stage 2: 公開readerを追加

1. `CatalogReader.getEntryDetail`を`CatalogWordRef`入力で定義する。
2. `ConjugationReader.getConjugation`と`hasConjugation`を定義する。
3. methodがraw `int`、`WordType`、`SearchDirection`、`DictionaryDirection`を受け取らないことを確認する。

### Stage 3: legacy mapperを実装

1. Esp→Jpn dictionary entityからpublic DTOへのpure mapperを実装する。
2. Jpn→Esp dictionary entityからpublic DTOへのpure mapperを実装する。
3. conjugation entityからpublic DTOへのpure mapperを実装する。
4. nullable collectionを空Listへ正規化するかnullを維持するかは、表示上の意味を確認してfieldごとにcontract testで固定する。機械的に意味を変えない。

### Stage 4: legacy reader adapterを実装

1. `LegacyCatalogReaderAdapter`へ方向別dictionary Repositoryをconstructor injectionする。
2. `CatalogId`で分岐し、対応するRepositoryへ`word.wordId`を渡す。
3. successだけをDTOへmapし、failureの`AppError`を同一instanceで伝播する。
4. `LegacyConjugationReaderAdapter`へ`IConjugacionsRepository`を注入する。
5. Esp→Jpnでは既存methodを呼び、Jpn→EspはRepositoryを呼ばずunsupported failureを返す。

### Stage 5: app compositionを追加

`app/bootstrap`配下にCatalog compositionを置き、次を提供する。

- `CatalogReader` provider → `LegacyCatalogReaderAdapter`
- `ConjugationReader` provider → `LegacyConjugationReaderAdapter`

既存`core/di/data/repository_di.dart`のlegacy providerはこの段階では残す。新providerが未使用でも、composition testで同じdependency graphからresolveできることを確認する。Catalog内部providerをconsumerが直接importする形にはしない。

### Stage 6: testでseamを固定

最低限、次のtestを追加する。

1. public port dependency test
   - port配下がlegacy core entity／Repository、Flutter、他featureをimportしない
2. mapper test
   - nested data、nullability、collection immutabilityを含む全field mapping
3. Catalog reader adapter test
   - Catalog IDごとに正しいRepositoryだけを呼ぶ
   - raw word IDが正しくunwrapされる
   - failure identityを維持する
4. Conjugation reader adapter test
   - Esp→Jpnのconjugation／hasを委譲する
   - Jpn→Espはlegacy Repositoryを呼ばずunsupported failureになる
5. composition test
   - provider overrideを使い、新readerがresolveされる

### Stage 7: regression確認

既存consumerを切り替えていないため、既存のSearch、WordDetail、Quiz、Ranking、WordStatus testがそのまま成功することを確認する。特に次を重点対象とする。

- `test/unit/core/application/catalog_fetch_usecase_test.dart`
- `test/unit/features/word_page/application/query/load_word_detail_query_test.dart`
- `test/unit/features/search/**`
- `test/unit/features/quiz/**`
- `test/unit/features/ranking/**`

## 6. リスクと対策

### 公開DTOがlegacy entityの別名になる

wrapperやtypedefを使わず、adapterで明示的にfield mappingする。これにより移行順序6で内部entityを移動してもconsumer contractを維持できる。

### `CatalogReader`が万能Repositoryになる

detailとconjugationに限定し、Search pagination、Quiz rule、Ranking projection、status writeを追加しない。consumer固有queryはconsumer側に残す。

### 方向差をnullable fieldへ隠す

sealed variantで表現し、unsupported conjugationは明示的failureにする。

### mapper追加時に情報を失う

現行画面が読むnested fieldをfixture化し、全field mapping testを先に書く。HTML contentは加工せずそのままcontractへ渡す。

### 新旧DIが二重の正本に見える

legacy providerは実装資源、Catalog providerは外部利用contractと位置づける。新規consumerはCatalog portだけへ依存し、legacy providerの削除は全consumer移行後に行う。

### error semanticsが方向別に変わる

adapterはfailureを包み直さず伝播する。既存のempty／not-found差はこの段階で統一せずcharacterization testに残す。

## 9. 次の移行への引き継ぎ

移行順序4では、Quiz-ownedの`QuizCandidateSource`を定義し、Catalog内部adapterで実装してQuiz→Search依存を除去する。汎用`CatalogReader`へQuiz専用methodを追加してはならない。

移行順序5では、WordDetailが`CatalogReader`／`ConjugationReader`を利用するように切り替え、Catalog側の能力確認を経てrouteから`hasConj`を除去する。その際に既存deep linkの`type`／`hasConj` parameterをどう互換parseするかを別途確定する。
