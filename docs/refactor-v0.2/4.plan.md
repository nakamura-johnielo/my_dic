# 移行順序4: Quiz→Search依存をQuiz-owned portとCatalog adapterへ置き換える

- 状態: 実施前
- 対象: [`concept.md`](./concept.md) の「移行順」4
- 前提: [`3.plan.md`](./3.plan.md) のCatalog公開port／legacy adapterが実装・検証済み
- 成果物の性質: Quiz候補検索境界の切り出しと既存consumerの切替
- DB／Firebase／同期protocol／route変更: なし

## 1. 目的

Quizの候補検索がSearch featureのquery、result model、use case、DIを借りている状態を解消する。Quizが必要とする候補検索contractをQuiz application側に定義し、現行Catalog／Rankingデータを読むprovider-side adapterで実装する。

現在の依存は次のとおりである。

```text
QuizSearchViewModel
  -> ISearchWordUseCase.executeQuiz
  -> SearchQuery / SearchDirection
  -> SearchResultPage / ConjugationSearchItem
  -> ISearchQueryRepository.searchQuiz
  -> DriftSearchQueryRepository / SearchQueryDao.fetchQuizItems
```

移行後は次の形にする。

```text
Quiz presentation
  -> Quiz application model / QuizCandidateSource
                              ^
                              |
                 Catalog-backed legacy adapter
                              |
                 existing read-only data sources
```

このスライスでは、Quiz画面から見える検索結果、順序、ページング、ランキング、語義、star count、部分失敗、再試行、quiz gameへの遷移を維持する。候補検索を汎用`CatalogReader`へ追加したり、Searchのpublic modelを共通modelへ昇格させたりしない。

## 2. 現行contractのcharacterization

実装前に次の挙動をtestで固定する。

| 項目 | 現行の意味 |
|---|---|
| 対象Catalog | Esp→Jpnのみ |
| query | `trim()`後の非空文字列 |
| page | 0-based |
| page size | 画面では30件 |
| primary result | `getQuizConjugacionByWordWithPage(text, size, page)`の順序を維持 |
| candidate identity | Esp→Jpnのword ID |
| 表示情報 | headword、plain-text meaning、ranking number、star count |
| `hasNext` | primary result件数が`size`と等しい場合にtrue |
| enrichment失敗 | primary resultは成功扱いとし、source別warningを返す |
| primary query失敗 | query全体を`DatabaseError` failureにする |
| stale response | query変更後または後続request開始後の古いresponseを破棄 |
| page merge | page 0は置換、page 1以降は末尾へ追加 |

`matches`は現行`ConjugationSearchItem`に含まれるが、Quiz候補一覧・route・game初期化のいずれでも読まれていない。characterizationで未使用を確認できた場合、Quiz公開modelには含めない。表示または選択ruleで実際に必要と判明した場合だけ、Quiz-ownedの明示的なfieldとして追加する。

## 3. 設計方針

### 3.1 portとmodelはQuizが所有する

```text
lib/features/quiz/
├── application/
│   └── candidate_search/
│       ├── quiz_candidate_source.dart
│       ├── quiz_candidate_query.dart
│       ├── quiz_candidate.dart
│       ├── quiz_candidate_page.dart
│       └── quiz_candidate_issue.dart
└── presentation/
    ├── ui_model/quiz_search_model.dart
    └── view_model/quiz_search_view_model.dart
```

初期contractは次の形とする。命名は実装時のDart規約に合わせて調整できるが、責務と情報量を増やさない。

```dart
abstract interface class QuizCandidateSource {
  Future<Result<QuizCandidatePage>> search(QuizCandidateQuery query);
}

final class QuizCandidateQuery {
  const QuizCandidateQuery({
    required this.text,
    required this.page,
    required this.size,
  });

  final String text;
  final int page;
  final int size;
}

final class QuizCandidate {
  const QuizCandidate({
    required this.word,
    required this.headword,
    required this.meaningText,
    required this.rankingNo,
    required this.starCount,
  });

  final CatalogWordRef word;
  final String headword;
  final String? meaningText;
  final int? rankingNo;
  final int? starCount;
}
```

- identityはraw `int`だけで公開せず、`CatalogWordRef(CatalogId.espJpnMain, wordId)`を使う。
- Quizは`SearchDirection`、`SearchQuery`、`SearchResultPage`、`ConjugationSearchItem`をimportしない。
- `QuizCandidatePage`はimmutableな候補List、`hasNext`、immutableなissue Listを持つ。
- `QuizCandidateIssue`は`source`と`AppError`を持ち、presentationで`QueryWarning`へ変換できるようにする。
- contractはFlutter、Riverpod、Drift、DAO、Search presentation型をimportしない。
- 空queryの拒否、`page >= 0`、`size > 0`はcontract testで固定する。assertだけに依存せず、外部入力に対するfailure semanticsを明示する。

### 3.2 adapterはQuiz portを実装し、Catalog内部の語彙能力を利用する

provider-side integration adapterを次へ置く。

```text
lib/features/catalog/internal/infrastructure/legacy/quiz_candidate/
├── legacy_quiz_candidate_source_adapter.dart
├── legacy_quiz_candidate_mapper.dart
└── legacy_quiz_candidate_enrichment.dart
```

このadapterだけは、dependency inversionの実装点としてQuiz-owned application portをimportできる。Catalogのdomain／public port／既存`CatalogReader`／`ConjugationReader`はQuizをimportしてはならない。

adapterは現行の次の処理をSearchから移す。

1. conjugation datasourceによるpaged primary query
2. primary rowから`QuizCandidate`へのmapping
3. conjugation／dictionaryからのplain-text meaning補完
4. dictionary headwordからのstar count算出
5. ranking tableからのread-only ranking補完
6. enrichmentごとの部分失敗収集
7. primary件数による`hasNext`判定

`DriftSearchQueryRepository`や`SearchQueryDao`へ委譲して依存を隠してはならない。Search-ownedの`SearchRankingLookup`、`extractMeaningText`、`starCountFromHeadword`もimportせず、候補projectionに必要なpure mappingとread lookupをadapter側へ移す。重複実装を恒久化せず、移動後にSearchとQuizの両方が必要とするpureなCatalog表現変換が判明した場合のみ、consumer非依存のCatalog internal helperへ抽出する。

### 3.3 primary failureと部分失敗を区別する

- primary conjugation queryの例外は`DatabaseError(message: 'Unable to search quiz candidates.')`へ変換し、`Result.failure`で返す。
- meaning、ranking、star countの各enrichment失敗はcandidate page自体を失敗させない。
- enrichment errorが既に`AppError`なら同じinstanceをissueへ保持する。
- 非`AppError`はsourceを識別できる`DatabaseError`へ変換する。
- enrichment失敗時のfieldは`null`とし、候補の順序・件数・`hasNext`を変更しない。
- 空のprimary resultではenrichment queryを実行しない。

warning source名は既存互換の`ranking`、`meaning`、`starCount`を維持する。message文言をUI contractとして扱っているtestがある場合は、既存文言も維持する。

### 3.4 DIはapp compositionで結線する

`QuizSearchViewModel`がSearch DIを直接読む状態を廃止する。`app/bootstrap`のcompositionで、既存datasource／database providerから`LegacyQuizCandidateSourceAdapter`を構築し、Quizの`QuizCandidateSource` providerへ渡す。

```text
quizSearchViewModelProvider
  -> quizCandidateSourceProvider (Quiz contract)
  -> LegacyQuizCandidateSourceAdapter (compositionで具象化)
```

- `lib/features/quiz/di/view_model_di.dart`から`features/search/di/usecase_di.dart` importを削除する。
- provider overrideでfake sourceを注入できる構造にする。
- adapterの具象型をpresentationから参照しない。
- 既存Catalog compositionと同じapp bootstrap entry pointへ集約し、別のdatabase graphを作らない。

### 3.5 presentationのSearch型をQuiz型へ置換する

`QuizSearchViewModel`は`QuizCandidateSource`と`QuizCandidateQuery`だけを使う。世代番号によるstale response抑止、loading中の多重load拒否、previous data保持、page merge、warning変換は維持する。

`QuizSearchState`／`QuizSearchResults`のitem型を`QuizCandidate`へ変更し、`QuizSearchFragment`は次の変換だけを担当する。

- `candidate.word.wordId`を既存`QuizGameRoute.wordId`へ渡す
- `candidate.headword`を既存route queryの`word`へ渡す
- meaning、ranking、star countを既存card表示へ渡す

このスライスでは`QuizGameRoute`を`CatalogWordRef`化しない。route path／parameterの変更を混ぜず、route境界でのみraw IDへunwrapする。

`app/presentation/search_card.dart`経由の共有cardは、Search application型をQuizへ漏らしていないため維持する。UI部品自体のownership整理は移行順序11または別sliceとし、今回の候補検索境界と同時に見た目を変更しない。

### 3.6 SearchからQuiz専用APIを削除する

Quizの切替とadapter testが成功した後、Searchから次を削除する。

- `ISearchWordUseCase.executeQuiz`
- `SearchWordInteractor.executeQuiz`
- `ISearchQueryRepository.searchQuiz`
- `DriftSearchQueryRepository.searchQuiz`
- `SearchQueryDao.fetchQuizItems`
- Search result pageをQuiz出力として扱うtest／コメント

通常の`execute`、`search`、Search画面のconjugation suggestionは残す。`fetchConjugationSuggestions`はSearch固有の補助検索であり、Quiz候補検索とは別contractである。

legacy coreの`getQuizConjugacionByWordWithPage`と同名datasource methodはadapterの互換入力としてこの段階では残せる。Catalog内部entity／Repository／DAOの物理移動と、Quiz語彙を含まないneutralな内部命名への変更は移行順序6で行う。未使用になったlegacy methodだけは参照を確認したうえで削除し、DB query自体は変更しない。

## 4. 実施手順

### Stage 0: preflightとcharacterization test

1. 移行順序3のCatalog test、Quiz test、Search test、`flutter analyze`が成功することを確認する。
2. 現行Quiz候補検索のprimary順序、page、`hasNext`、enrichment、warning、failureをfixtureで固定する。
3. `QuizSearchViewModel`のstale response、previous data、page merge、多重load拒否をtest化する。
4. `matches`がQuiz presentation／route／gameで未使用であることを`rg`とtestで確認する。

### Stage 1: Quiz-owned contractを追加

1. `QuizCandidateQuery`、`QuizCandidate`、`QuizCandidatePage`、`QuizCandidateIssue`を追加する。
2. `QuizCandidateSource.search`を追加する。
3. collection immutability、identity、query validation、failure typeをcontract testで固定する。
4. Quiz application contractからSearch／Flutter／Riverpod／Drift importが0件であることを確認する。

### Stage 2: Catalog-backed adapterを実装

1. existing conjugation datasourceへpaged queryを委譲するadapterを追加する。
2. rowをEsp→Jpnの`CatalogWordRef`とQuiz candidateへmapする。
3. meaning、ranking、star countのbulk enrichmentを移植する。
4. primary failureとsource別の部分失敗を分離する。
5. 空結果、最終page、重複ID、欠損enrichmentをtestする。
6. adapterがSearch型／Search repository／Search DIをimportしていないことを確認する。

### Stage 3: compositionを追加

1. app bootstrapでadapterを既存database／datasource graphへ接続する。
2. Quiz DIへ`QuizCandidateSource` providerを追加する。
3. provider overrideによるfake注入と実adapterのresolveをcomposition testで確認する。

### Stage 4: Quiz consumerを切り替える

1. `QuizSearchViewModel`のdependencyを`ISearchWordUseCase`から`QuizCandidateSource`へ変更する。
2. Search query生成を`QuizCandidateQuery`生成へ置換する。
3. `QuizSearchResults.items`を`List<QuizCandidate>`へ変更する。
4. fragmentのtap／card mappingをQuiz candidateへ変更する。
5. Quiz配下の全Search application／DI importを削除する。
6. 現行UI、route parameter、pagination開始値が変わっていないことをwidget／view model testで確認する。

### Stage 5: SearchからQuiz branchを削除

1. `executeQuiz`、`searchQuiz`、`fetchQuizItems`をinterfaceと実装から削除する。
2. SearchのQuiz専用testをQuiz／Catalog adapter testへ移す。
3. Search通常検索とconjugation suggestionのregression testを実行する。
4. `features/search`内にQuiz専用のmethod、comment、model利用が残っていないことを確認する。

### Stage 6: regressionとboundary確認

1. Quiz candidate contract／adapter／view model／widget testを実行する。
2. Search application／data query／view model testを実行する。
3. Quiz gameのconjugation取得とroute testを実行し、候補選択後の画面が維持されることを確認する。
4. Catalog reader testとapp bootstrap composition testを再実行する。
5. 全体`flutter analyze`と`git diff --check`を実行する。

## 7. リスクと対策

### Search modelを名前だけQuizへ複製する

Quizで必要なfieldだけをcontractに含める。Search方向、通常検索item、conjugation suggestion、Search固有flagを持ち込まない。identityは`CatalogWordRef`を再利用する。

### adapter移植で検索結果が変わる

移植前後に同じfixtureを通し、primary順序、page offset、`hasNext`、meaning fallback、ranking selection、star count、warning sourceを比較する。query SQLやdatasource methodはこのスライスで変更しない。

### enrichment失敗で候補全体が消える

primary queryとoptional enrichmentを別のerror boundaryに置く。各enrichmentを個別にcaptureし、候補を成功として返す既存の部分成功を維持する。

### adapterがCatalogのpublic APIをQuiz化する

既存`CatalogReader`／`ConjugationReader`へ候補検索methodを追加しない。Quiz portへの依存をintegration adapter一か所に限定し、Catalog public portとdomainからQuiz importが0件であることをtestする。

### Search削除を先に行い、切替途中でbuild不能になる

Quiz contractとadapterをadditiveに完成させ、compositionとconsumer切替後にSearch branchを削除する。各Stage終了時に対象testを実行する。

### shared cardまで同時に移動してUI差分が広がる

app-level facade経由の現行cardを維持する。component ownership、status UI、directory renameは別sliceへ分離する。

### legacy内部APIにQuizという語が残る

この段階ではDB query互換を優先する。Search→Quiz依存除去の完了条件と、Catalog内部の物理移動／neutral namingを分け、後者を移行順序6へ明示的に引き継ぐ。

## 10. 次の移行への引き継ぎ

移行順序5では、WordDetailが`CatalogReader`／`ConjugationReader`から能力を確認する経路へ切り替え、`WordDetailRoute`から`hasConj`を除去する。今回の`QuizGameRoute`は変更対象に含めない。

移行順序6では、legacy coreに残るWord／Dictionary／Conjugation entity、Repository、datasource、DAO、mapperをCatalogへ移す。その際、`getQuizConjugacionByWordWithPage`のようなconsumer名を持つ内部APIをneutralなCatalog capabilityへ変更し、今回追加したadapterの依存先を新Catalog内部実装へ差し替える。Quiz-ownedの`QuizCandidateSource` contractとpresentationは維持する。
