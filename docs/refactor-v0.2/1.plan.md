# 移行順序1: Catalog・WordStatus・MyWordのownershipをADRで固定する

- 状態: 実施前
- 対象: [`concept.md`](./concept.md) の「移行順」1
- 成果物の性質: documentation-only
- production code変更: なし
- DB／Firebase／同期protocol変更: なし

## 1. 目的

後続のリファクタで「共有されているから`core`へ置く」「型が似ているから統合する」といった配置先起点の判断を避けるため、Catalog、WordStatus、MyWordの業務上のownerと境界をADR（Architecture Decision Record）で先に固定する。

このスライスの完了時点では、ディレクトリ、import、型、Repository、DI、DB schema、Firebase collection、同期payload、画面挙動を一切変更しない。変更するのはarchitecture文書だけである。

このADRは、少なくとも後続の移行順序2〜9に対して次の判断基準を提供する。

- どのfeatureが正本となるdomain model／application contractを所有するか
- 他featureが何を直接参照せず、どの公開portを通して利用するか
- 現在の物理配置と論理ownershipが異なる箇所を、過渡状態としてどう扱うか
- 似ていてもライフサイクルが異なるCatalog wordとMyWordを統合しない理由
- 辞書方向別のWordStatusをどこまで統合し、何を互換adapterとして残すか
- feature ownershipとDB／同期基盤のownershipをどう区別するか

## 2. このスライスで固定する決定

ADRは「Catalog、WordStatus、MyWordの境界」という一つの設計判断を扱う。3つを別々のADRに分割すると、`MyWordStatus`の帰属やCatalog wordとstatusの関係がADR間でずれる可能性があるため、この段階では一つの原子的なADRにまとめる。

### 2.1 ownerの意味

本計画でいうownerは、ファイルが現在置かれているディレクトリでも、データを所有するaccountでもない。次に責任を持つ論理moduleを指す。

- 用語とinvariantの正本を定義する
- domain modelと業務ruleを変更する権限を持つ
- 外部利用者向けの最小port／contractを定義する
- 永続化modelとのmappingを管理する
- 変更時に影響を受けるconsumerと互換性を判断する

「account-owned data」のownerはユーザー識別上の所有者であり、「feature ownership」とは別概念であることをADR内で明記する。

### 2.2 Catalogのownership

Catalogを、アプリが配布・参照する辞書マスタと、その語彙知識を所有する業務moduleとする。

Catalogが所有するもの:

- Catalog内で一意なword identityの概念
- 見出し語、語義、辞書entry、example、idiom、supplement、品詞
- 辞書データから導出できるconjugationと「活用を持つか」の判定
- 西日／日西というCatalog variantごとのdomain model
- 辞書検索・詳細取得・活用取得に必要な公開read portと、その内部adapter
- 辞書master用Repository、DAO、mapperの業務上のownership

Catalogが所有しないもの:

- `isLearned`、`isBookmarked`、`hasNote`などのユーザー別状態
- MyWordとMyWordStatus
- Searchのquery／pagination／result enrichment orchestration
- WordDetailの画面用aggregationと表示state
- Quizの出題rule、game state、score
- Rankingのfilter／pagination／画面projection
- route URL、navigation、app-level composition
- database connectionの生成・破棄や汎用transaction runtime

西日と日西は同じCatalog owner配下のvariantとするが、巨大なnullable entityには統合しない。構造差はCatalog内部で明示的な型またはadapterとして保持する。

現在の`JpnEspWord` entityに存在する`isLearned`／`isBookmarked`／`hasNote`はCatalog word本体の正本と見なさない。これらの正本はWordStatusであり、Catalog wordとユーザー状態を同時に必要とする画面ではquery projectionとして合成する。フィールドの実削除は移行順序9まで行わない。

`CatalogId`と`CatalogWordRef`の具体的なDart API、enum値、validation、serializationは移行順序2で定義する。本ADRでは「identity contractはCatalogが所有し、consumer独自の`WordType`やdirection flagを正本にしない」という責務だけを固定する。

### 2.3 WordStatusのownership

WordStatusを、accountとCatalog wordの組に付随する学習状態を所有する業務moduleとする。

WordStatusが所有するもの:

- Catalog wordを対象とする`isLearned`、`isBookmarked`、`hasNote`
- 状態のwatch／updateと、その業務上のinvariant
- account scopeを含むstatus identityの意味
- 西日／日西で共通化するdomain modelとapplication contract
- direction別の既存保存形式と共通modelを接続するmapper／adapter
- 辞書status向けのpresentation contractと、共通status button UI

WordStatusが所有しないもの:

- Catalog word本体、辞書entry、conjugation
- MyWordStatus
- account/sessionの正本
- 汎用SyncEngine、queue、checkpoint、retry、scheduling
- appがどのdirection別実装を注入するかというcomposition

西日／日西の論理domain modelとapplication contractは一つにする。一方、次の外部互換境界は移行順序8までは方向別adapterとして維持する。

- Drift tableと既存column／primary key
- Firebase collectionとdocument contract
- remote／local DTOとmapper
- sync handlerのdataset別接続
- `SyncDataset.espJpnWordStatus`と`SyncDataset.jpnEspWordStatus`のstable ID

したがって「domain/applicationを統合すること」と「物理datasetを一つにmigrationすること」は同義ではない。後者は本リファクタの要求に含めない。

### 2.4 MyWordのownership

MyWordを、ユーザーが作成・編集・削除する個人辞書項目と、そのライフサイクルを所有する独立featureとする。

MyWordが所有するもの:

- UUID文字列によるMyWord identity
- word、contentsと登録validation
- create／read／update／delete、tombstone、account scope
- MyWord固有のlocal-first writeと同期mapping
- MyWordに従属するMyWordStatus
- `my_word_status`が`my_words`より後に同期される依存制約

MyWordが所有しないもの:

- Catalog wordと辞書master
- Catalog word向けWordStatus
- Catalogのidentity／read port
- 複数sourceを横断する一覧のread model
- 汎用SyncEngine、queue、checkpoint、retry、scheduling

Catalog wordとMyWordは、ID形式、書き込み可否、account scope、削除、同期、validationのライフサイクルが異なるため、同じwrite modelや共通基底entityへ統合しない。同じ一覧に表示する要件が生じた場合は、consumerまたは将来のLibrary系featureがread model／query projectionとして合成する。

現在`MyWord` entityに存在する`isLearned`／`isBookmarked`はMyWord本体の正本と見なさない。MyWordStatusが正本であり、一覧表示用の値はquery projectionで合成する。フィールドの実削除は移行順序9まで行わない。

### 2.5 MyWordStatusの扱い

MyWordStatusは、少なくとも次の差が解消されるまではMyWord owner配下に残す。

- identityがCatalog wordの整数IDではなくMyWordのUUID文字列である
- MyWord削除にライフサイクルが従属する
- `my_word_status -> my_words`の同期順序制約がある
- `hasNote`のlocal table／outbox、remote DTO、Firestore rule、UI contractが一致していない

辞書WordStatusとの共有範囲は、現時点ではstatus button UIと小さなpresentation操作contractまでとする。将来、identity、field、削除、同期、競合解決の契約が実際に一致した場合のみ、別ADRで共通の`StudyItemStatus`等への昇格を検討する。

### 2.6 横断基盤との責務分担

ADRにはfeature ownershipだけでなく、横断基盤との分担も記録する。

| 関心事 | owner | feature側の責務 |
|---|---|---|
| 起動時の依存組み立て | `app/bootstrap` | 公開portと具象adapterを提供する |
| route／navigation | `app/routing`と各presentation consumer | Catalog identityを受け渡すがdomain truthを複製しない |
| DB connection／transaction runtime | database infrastructure | 各featureがschemaの意味とmapperを所有する |
| sync engine／queue／checkpoint／retry | `sync` | 各featureがdataset adapter、payload mapping、競合ruleを所有する |
| account/session解決 | `app/session` | featureは明示されたaccount scopeを契約に従って使う |
| 複数ownerのread合成 | consumerのapplication query、または専用read feature | write modelを統合せずprojectionを作る |

物理的に共通`DatabaseProvider`へtable登録が残っていても、tableの業務上のownerまで`core`になるわけではない。同様に、`SyncDataset`のstable IDがsync共通contractに置かれていても、payloadの意味やdataset固有mappingは各featureが所有する。

## 5. 実施手順

### Stage 0: preflightと変更範囲の固定

1. `git status --short`で既存の変更を確認し、ユーザーの変更を作業対象に含めない。
2. `docs/architecture/decisions/`と既存ADRの有無を再確認し、ADR番号の衝突を避ける。
3. 3章の根拠ファイルが存在し、symbolと責務が変わっていないか確認する。
4. このスライスをdocumentation-onlyとして宣言し、`lib/**`、`test/**`、`firestore.rules`、`pubspec.yaml`、生成物を変更対象から除外する。

停止条件:

- 並行作業で同じownershipを決めるADRが既に追加されている
- 現行実装が変わり、MyWordStatusのidentity／削除／同期依存がWordStatusと既に一致している
- `CatalogId`相当の別の正本が導入済みで、所有者が競合している

該当時は新ADRを重複作成せず、既存decisionの更新またはsupersedeが必要かを先に判断する。

### Stage 1: ADR基盤を作る

1. `docs/architecture/decisions/README.md`を作る。
2. 状態遷移、採番、supersede方法、必須sectionを短く定義する。
3. ADR一覧tableを置き、ownership ADRを登録する。

このREADMEは汎用的な文書基盤だけを提供し、architecture ruleや機能要件を新規追加しない。

### Stage 2: Contextとdecision driversを書く

1. 現在の論理概念が`core`、3つのstatus feature、MyWordへ分散している事実を書く。
2. current pathとtarget ownershipを分離して記載する。
3. 次の6軸をowner判定基準として明示する。
   - source of truth
   - identity
   - create／update／delete lifecycle
   - account scope
   - transaction／sync coupling
   - independent reason to change
4. 過去文書の命名やフォルダ案ではなく、production codeの振る舞いを根拠にする。

### Stage 3: ownershipと境界を記録する

1. 2章のCatalog、WordStatus、MyWord、MyWordStatusの決定をADRへ移す。
2. owner／non-ownerをmatrix化し、重複または空白の責務がないか確認する。
3. app、sync、database runtime、consumer queryとの境界を記す。
4. dependency directionを次の形で明記する。

```text
Search / WordDetail / Quiz / Ranking
                 |
                 v
          Catalog public port
                 ^
                 |
        Catalog internal adapter

CatalogWordRef <--- WordStatus public contract

MyWord <--- MyWordStatus
  ^             |
  +-------------+ lifecycle / sync dependency

app/bootstrap: public contractとadapterの結線のみ
sync: engineを所有し、datasetの業務意味は各featureが所有
```

5. 図だけに規範を持たせず、同じ内容を本文で明文化する。

### Stage 4: compatibilityと非目標を固定する

このADRの採用だけでは次を変えないと明記する。

- ユーザーから見える機能、画面、status buttonの挙動
- route path／query parameter／deep link
- 検索結果、辞書詳細、Quiz、Rankingの業務結果
- MyWordのvalidation、CRUD、guest/account scope
- Drift schema version、table名、column名、primary key、foreign key
- Firebase collection／document／Security Rules
- `SyncDataset`のstable ID、outbox payload、field mask、競合rule
- guest migrationのtransactionと対象dataset
- 公開済みの型やRepositoryの即時rename／move

`MyWordStatus.hasNote`の不一致は、このADRで仕様を追加または削除して解消しない。既知の差として記録し、MyWordStatusを統合しない根拠にする。

### Stage 5: 代替案と帰結を記録する

Rejected alternativesは「好み」ではなく、identity、lifecycle、coupling、migration riskのどれに反するかを記す。

Consequencesには最低限、次を含める。

- positive: source of truthとdependency directionが明確になる
- positive: schema／sync protocolを維持したまま段階移行できる
- positive: CatalogとMyWordの不要なunion分岐を避けられる
- negative: 移行中はadapterと旧pathが併存する
- negative: 物理配置だけを見てもownerを判断できない期間がある
- trade-off: read projectionが増えてもwrite modelの純度を優先する

### Stage 6: 導線と後続作業を接続する

1. ADR indexからownership ADRへlinkする。
2. [`concept.md`](./concept.md)の移行順序1からADRへlinkする。
3. ADRのFollow-upに移行順序2〜11との対応表を置く。
4. 移行順序2の入口として、次だけを引き継ぐ。
   - identity contractのownerはCatalog
   - `CatalogId`／`CatalogWordRef`の具体設計は未実装
   - 既存`WordType`／`SearchDirection`／`DictionaryDirection`との変換箇所を次スライスで棚卸しする
   - route、DB、serializationへの反映は各後続スライスのscopeに従う

### Stage 7: 文書レビューとaccept

1. ADR内の規範語を確認し、`must`相当の決定と将来案を混同していないかレビューする。
2. `Current state`、`Decision`、`Follow-up`の時制を分ける。
3. relative linkと参照pathを検証する。
4. 合意済みの設計判断として採用する時点でADRを`Accepted`にする。
5. `concept.md`側には要約を複製せず、ADRへのlinkとsource-of-truth注記だけを残す。

## 8. リスクと対策

### ADRが将来のfolder構成を固定しすぎる

対策: owner、invariant、dependency directionを決め、`port/`と`internal/`などの具体folder名は参考構造に留める。directory整理は移行順序11の判断余地を残す。

### 論理ownershipと物理table ownershipを混同する

対策: domain semantics、schema meaning、database runtime、sync orchestrationを別の行でmatrix化する。「tableが共通DatabaseProviderに登録されるためcore-owned」とは判断しない。

### WordStatus統合がprotocol統合へ拡大する

対策: direction別table／collection／stable IDをcompatibility constraintとしてADRに明記する。protocol変更が必要なら別ADRとmigration計画を要求する。

### MyWordStatusの未整合を共通仕様として固定する

対策: `hasNote`差異を既知の未整合として明示し、共通domainへの統合条件を満たしていないと記録する。値や機能はこのスライスで追加・削除しない。

### ADRとconceptが二重のsource of truthになる

対策: `concept.md`はrationale／roadmap、Accepted ADRはownershipの規範と役割を分ける。判断変更時はADRをsupersedeし、両文書へ同じ長文を複製しない。

### historical documentへ引きずられる

対策: `docs/refactor-v0.1/**`は参考情報としてのみ扱う。現行production code、現在の契約、変更理由の独立性を優先し、旧planの完了状態を新ADRへ転記しない。

## 11. 次の移行への引き継ぎ

移行順序2はAccepted ADRを入力として、Catalog-owned public identity contractだけを小さく実装する。開始前に次を満たすこと。

- ADRが`Accepted`である
- Catalog、WordStatus、MyWord間に未割当の責務がない
- `CatalogWordRef`がCatalogの内部entityを外部公開するためのものではなく、最小のidentity valueであると合意されている
- 既存route、Search、WordDetail、Quiz、Ranking、WordStatusが使う識別子／direction表現の棚卸し先がFollow-upに列挙されている
- schemaやsync stable IDを変えずにadapterで変換する方針が維持されている

この条件を満たすまでは、移行順序2の型追加やdirectory移動を先行させない。
