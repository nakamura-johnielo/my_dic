# 移行順序8: DB／Firebase／SyncDatasetを変更せずWordStatus infrastructureをadapter化する

- 状態: 実施前
- 対象: [`concept.md`](./concept.md) の「移行順」8
- 前提: [`7.plan.md`](./7.plan.md) の辞書WordStatus domain／application／presentation統合が実装・検証済み
- 成果物の性質: `features/word_status`が所有する方向別local／remote adapter、単一の同期algorithm、WordStatus-owned guest migration capability、一本化されたcomposition
- DB／Firebase data migration: なし
- Drift schema version／table名／column名／PK／FK／index／asset DB変更: なし
- Firebase collection名／document path／field名／値表現変更: なし
- `SyncDataset` enum case／stable ID／outbox payload／checkpoint key変更: なし

## 1. 目的

順序7で共通化した辞書WordStatusのdomain／application境界より下に残る、方向別のDrift、Firebase、同期、DIを`features/word_status/internal/infrastructure`へ集約する。

現状の業務入口は共通化されているが、永続化と同期のownerは旧Feature名と`core`へ分散している。

```text
features/word_status application
  -> direction adapter
     -> core/infrastructure/datasource/word_status
        -> core/.../EspJpnWordStatusDao
     -> core/infrastructure/datasource/jpn_esp_word_status
        -> core/.../JpnEspWordStatusDao

app/sync_composition
  -> features/esp_jpn_word_status/di
     -> EspJpnWordStatusSyncHandler -> Firebase WordStatus
  -> features/jpn_esp_word_status/di
     -> JpnEspWordStatusSyncHandler -> Firebase JpnEspWordStatus

app/guest_migration
  -> 2つのdirection別core local datasource
```

この配置では、辞書WordStatusの変更理由が`features/word_status`、旧direction Feature、`core`、app workflowの4か所へ分散する。また2つのsync handlerはdatasetとDTO型以外がほぼ同一であり、retry、lease、cancellation、pending field保護、checkpoint更新の修正を二重に行う必要がある。

移行後は次へ収束させる。

```text
features/word_status/
├── application／domain／presentation
└── internal/infrastructure/
    ├── shared/
    │   ├── word_status_repository_adapter
    │   ├── word_status_dataset_sync_handler
    │   └── guest_migration_adapter
    ├── esp_jpn/
    │   ├── drift
    │   ├── firebase
    │   └── sync adapter
    └── jpn_esp/
        ├── drift
        ├── firebase
        └── sync adapter

app composition
  -> WordStatusの2 direction adapterを生成
  -> 同じWordStatusDatasetSyncHandlerをdataset別に2 instance登録
```

共通化するのは同期の制御algorithmとinfra-neutralな内部contractである。2つの物理table、Firebase collection、wire DTO、dataset identityは統合しない。MyWordStatusも対象外とする。

## 2. 移行前に固定するcontract

実装前に、両directionへ同じcharacterization suiteを適用し、次を移行前fixtureとして固定する。

### 2.1 Drift contract

| 項目 | Esp-Jpn | Jpn-Esp |
|---|---|---|
| table | `word_status` | `jpn_esp_word_status` |
| word ID column | `word_id` | `jpn_esp_word_id` |
| primary key | `(account_id, word ID)` | `(account_id, word ID)` |
| parent FK | `words.word_id`、cascade delete | `jpn_esp_words.jpn_esp_word_id`、cascade delete |
| bool storage | nullable integer `0／1` | nullable integer `0／1` |
| timestamp column | text `edit_at` | text `edit_at` |
| sync metadata | `local_revision`、`remote_revision`、`deleted_at`、`last_mutation_id` | 同左 |
| guest default | `legacy_unowned` | `legacy_unowned` |
| changed query | `>= since` | `> since` |

次も維持する。

- local patchはmissing rowなら3 boolの未指定値を`0`としてinsertし、既存rowなら指定fieldだけを更新する。
- local patchは`local_revision`を1増やす。
- remote applyは`local_revision`を増やさず、pending local fieldを上書きしない。
- remote acknowledgementはleased `local_revision`が一致する場合だけmetadataを更新する。
- row writeとoutbox enqueue、remote applyとcheckpoint write、guest migration全体のtransaction範囲を変えない。
- watchのmissing-row、`.distinct()`、account filterを変えない。
- Esp-Jpnの`>=`とJpn-Espの`>`の差は既知の現行差として固定し、本スライスでは揃えない。

### 2.2 Firebase contract

| 項目 | Esp-Jpn | Jpn-Esp |
|---|---|---|
| path | `User/{accountId}/WordStatus/{wordId}` | `User/{accountId}/JpnEspWordStatus/{wordId}` |
| document ID | decimal word ID string | decimal word ID string |
| identity field | `wordId` integer | `wordId` integer |
| bool wire value | `0／1` integer | `0／1` integer |
| ordered cursor | `updatedAt`、document ID | `updatedAt`、document ID |
| cursor boundary | inclusive `startAt` | inclusive `startAt` |

fieldは`wordId`、`isLearned`、`isBookmarked`、`hasNote`、`updateBy`、`createdAt`、`updatedAt`、`revision`、`lastMutationId`、`clientUpdatedAt`を維持する。Firestore timestampはUTCへ変換し、missing revisionは`0`、missing optional metadataは`null`とする。

方向別DTO名は内部実装名でありrename可能だが、定数値とmapper出力をsnapshot比較する。DTOを共通domain `WordStatus`へ変換しない。

### 2.3 outbox／SyncEngine contract

| 項目 | Esp-Jpn | Jpn-Esp |
|---|---|---|
| dataset enum | `SyncDataset.espJpnWordStatus` | `SyncDataset.jpnEspWordStatus` |
| stable ID | `esp_jpn_word_status` | `jpn_esp_word_status` |
| operation | `patch` | `patch` |
| entity ID | decimal word ID string | decimal word ID string |
| field mask order | `isLearned`、`isBookmarked`、`hasNote` | 同左 |
| checkpoint scope | account＋dataset | account＋dataset |

同期algorithmでは次を固定する。

1. 対象datasetのpending mutationだけをleaseする。
2. remote patch後、local metadata更新とqueue ackを同一transactionで行う。
3. stale acknowledgementはfailureとしてretry／dead-letter分類へ渡す。
4. pull前に対象datasetのpending fieldを取得し、同じentityの未ack fieldだけをremote applyから除外する。
5. cursorは`updatedAt`の秒／ナノ秒とdecimal document IDから作る。
6. remote applyとcheckpoint writeを同一local transactionで行う。
7. pushの一部が失敗してもpullを実行し、最終resultの`cursorUnchanged`を現行どおり算出する。
8. session fence／cancellationを各I/O境界とtransaction内で確認する。
9. batch limitは50、lease durationは2分、clock／retry／classifierのinjectabilityを維持する。
10. registryには2つの別dataset handlerを登録し、duplicate datasetを許可しない。

### 2.4 guest migration contract

- Esp-Jpn、Jpn-Espを別datasetとして順番に処理する。
- guest rowとaccount rowのboolはfieldごとにOR mergeする。
- merge後にguest rowを削除し、3 fieldすべてを含むpatch mutationをenqueueする。
- mutation IDは`{migrationId}:{dataset.stableId}:{wordId}`を維持する。
- `clientUpdatedAt`はlocal `edit_at`と同じ瞬間をUTC化して用いる。
- WordStatus、MyWord、MyWordStatus、UserProfileを含む全移行を一つのDatabase transactionで処理する。
- session fenceが無効なら全rowとoutbox mutationをrollbackする。
- detection summaryのdirection別countと表示順を変えない。

## 3. 設計方針

### 3.1 infrastructureのownerをWordStatusへ集約する

最終配置は次を基本とする。

```text
lib/features/word_status/internal/infrastructure/
├── word_status_repository_adapter.dart
├── sync/
│   ├── word_status_dataset_adapter.dart
│   ├── word_status_dataset_sync_handler.dart
│   └── word_status_sync_record.dart
├── guest_migration/
│   └── drift_word_status_guest_migration.dart
├── esp_jpn/
│   ├── drift/
│   │   ├── esp_jpn_word_status_dao.dart
│   │   ├── esp_jpn_word_status_local_data_source.dart
│   │   └── esp_jpn_word_status_local_store.dart
│   ├── firebase/
│   │   ├── esp_jpn_word_status_dto.dart
│   │   ├── esp_jpn_word_status_mapper.dart
│   │   ├── firebase_esp_jpn_word_status_dao.dart
│   │   └── firebase_esp_jpn_word_status_remote_store.dart
│   ├── esp_jpn_dictionary_word_status_adapter.dart
│   └── esp_jpn_word_status_dataset_adapter.dart
└── jpn_esp/
    ├── drift/
    ├── firebase/
    ├── jpn_esp_dictionary_word_status_adapter.dart
    └── jpn_esp_word_status_dataset_adapter.dart
```

命名はrepositoryの既存規約に合わせて微調整してよい。ただし完了時に次を満たす。

- `features/esp_jpn_word_status`と`features/jpn_esp_word_status`はdirectoryごと削除する。
- WordStatus DAO／local datasourceを`core`に残さない。
- direction名は物理adapterの識別としてだけ残し、domain／applicationへ戻さない。
- generated fileはsource移動後にbuild runnerで再生成し、手編集しない。

### 3.2 Drift table宣言とdatabase runtimeはschema bridgeとして扱う

本スライスで「DB tableを変更しない」とは、実DBのschemaと既存dataをそのまま利用し、WordStatus adapterの背後へ閉じ込めることを意味する。

`EspJpnWordStatus` table宣言はRankingのread projectionが参照し、`JpnEspWordStatus`はCatalog DAOのaccessor宣言に不要な形で混在している。両table classをただちに`word_status/internal`へ移すと、`ranking／catalog -> word_status/internal`という新しい禁止importが生まれる。

したがって本計画では次の順にする。

1. `JpnEspWordDao`の未使用`JpnEspWordStatus` accessor宣言を削除し、Catalogからstatus table dependencyを除去する。
2. direction別DAO／local datasourceはWordStatus internalへ移す。
3. table宣言、`DatabaseProvider`のtable registration、migration SQLは`core/infrastructure/database/drift`にschema runtime bridgeとして残す。
4. Rankingのstatus JOINをWordStatus port経由のprojectionへ変える順序9までは、Esp-Jpn table宣言を共有schemaとして扱う。
5. 全cross-feature table参照が解消した後、順序11の最終directory整理でtable宣言の物理配置を決定する。

これはtableの業務ownershipを`core`へ戻す判断ではない。write、sync、guest migrationのownerは本スライスでWordStatusへ移る。共有Drift databaseのregistration sourceだけを、内部import違反を増やさないために据え置く。

順序7の引き継ぎにある「Drift table／DAO／local datasourceを移す」は、この依存調査結果によりDAO／local datasource移動とtable schemaのadapter背後化へ具体化する。Dart table宣言の最終移動は順序9／11との重複を避けて延期する。

### 3.3 application用adapterとsync用adapterを分離する

順序7で導入した`DictionaryWordStatusAdapter`は画面用get／watch／updateだけを持つ。ここへsync、guest migration、Firebase DTO操作を追加しない。

```text
WordStatusRepositoryAdapter
  -> DictionaryWordStatusAdapter
     -> direction local store

WordStatusDatasetSyncHandler
  -> WordStatusDatasetAdapter
     -> direction local store
     -> direction remote store
```

同じdirection local storeを利用しても、公開するcapabilityを分ける。application use caseから`SyncDataset`、remote revision、outbox lease、Firebase DTOが見えない状態を維持する。

### 3.4 sync algorithmは一つ、wire adapterは二つにする

`WordStatusDatasetSyncHandler`へlease、push、ack、retry、pull、pending field保護、cursor、checkpoint、cancellationのalgorithmを一度だけ実装する。

内部contract例:

```dart
abstract interface class WordStatusDatasetAdapter {
  SyncDataset get dataset;

  Future<RemoteMutationAck> patch(RemoteMutationRequest request);
  Future<List<WordStatusSyncRecord>> fetchPage(
    String accountId,
    SyncCursor? cursor,
  );

  Future<T> transaction<T>(Future<T> Function() action);
  Future<bool> acknowledge(...);
  Future<void> applyRemote(
    WordStatusSyncRecord record, {
    required String accountId,
    required Set<String> skippedFields,
  });
}
```

`WordStatusSyncRecord`はsync internalのtransport-neutral recordとし、`wordId`、3 bool、UTC `updatedAt`、remote revision、last mutation IDだけを持つ。公開domain `WordStatus`や`CatalogWordRef`をFirebase wire DTOとして使わない。

方向別adapterが次を所有する。

- `CatalogId`と`SyncDataset`の対応。
- direction別local row／remote DTOから共通sync recordへのmapping。
- table data class、DAO、Firebase collection／field定数。
- Esp-Jpn／Jpn-Esp固有のerror context。

共通handlerが次を所有する。

- queue lease／ack／retry／dead-letter。
- pending field maskの集計。
- remote applyとcheckpoint更新の順序。
- result count、failure、cancellationの組み立て。

handlerは`adapter.dataset`だけを使い、Catalogからdatasetを推測しない。2つのadapterを一つのhandler instanceへ同時登録せず、datasetごとにhandler instanceを作る。これにより`DatasetHandlerRegistry`の一dataset一handler contractを維持する。

### 3.5 Firebase contractは共通化より封じ込めを優先する

direction別Firebase DTO、mapper、DAO、remote storeを各adapter配下へ移す。collection名をconstructor parameterにした巨大な汎用DAOへ統合しない。

理由は、現在の重複が小さい一方、field定数やcollection選択を誤ると既存remote dataから静かに分岐するためである。共通化対象は十分にcontract testできる同期制御algorithmまでとし、wire mappingは明示的な2実装を維持する。

`RemoteMutationTransaction`と`UserDTO.collectionName`は既存shared contractとして再利用する。patch時のidentity field、bool→`0／1` encode、inclusive cursor queryは変更しない。

### 3.6 guest migrationには公開capabilityを用意する

app workflowが移動後の`word_status/internal`やDrift row型を直接importしないよう、`features/word_status/application/port`にguest migration専用capabilityを置く。

```dart
abstract interface class WordStatusGuestMigration {
  Future<Map<CatalogId, int>> countGuestRows();

  Future<void> migrateGuestRows({
    required String accountId,
    required String migrationId,
    required DateTime Function() clock,
  });
}
```

実際のsignatureはtestabilityと既存clock contractに合わせて調整してよい。重要なのは、appへDrift data class、direction datasource、`SyncDataset` mappingを公開しないことである。

実装は2つのdirection local storeと`OutboxWriter`を受け、現在`MigrateGuestDataUseCase`に重複しているOR merge、guest delete、direction別outbox enqueueを行う。外側の`DatabaseProvider.transaction`とsession fenceはapp workflowに残し、MyWord／Profileを含む全体atomicityを維持する。

`DetectGuestDataUseCase`はdirection別countをこのcapabilityから受け、既存`GuestDataSummary`へ詰め直す。`MigrateGuestDataUseCase`はWordStatusの2 private methodをcapability呼出しへ置換する。MyWord／MyWordStatus／UserProfileの移行ロジックは変更しない。

### 3.7 compositionをapp bootstrapへ一本化する

`word_status_composition.dart`をWordStatus infra全体のcomposition rootとする。

```text
wordStatusInfrastructure
  -> databaseProvider
  -> firestoreDBProvider
  -> driftOutboxWriterProvider
  -> driftSyncQueueProvider
  -> driftSyncCheckpointStoreProvider
  -> syncExecutionGuardProvider
  -> 2 local store
  -> 2 remote store
  -> 2 DictionaryWordStatusAdapter
  -> 2 WordStatusDatasetAdapter
  -> WordStatusRepositoryAdapter
  -> 2 WordStatusDatasetSyncHandler instance
  -> WordStatusGuestMigration
```

循環importを避けるため、`word_status_composition.dart`が`sync_composition.dart`全体をimportしてhandler dependencyを取得する構造を作らない。shared sync infra providerを小さいapp bootstrap moduleへ抽出するか、sync compositionからfactory dependencyを渡す。完了時にapp bootstrap間のimport cycleが0件であることをtest／analyzeする。

`sync_composition.dart`は旧direction DIをimportせず、WordStatus compositionが公開する2 handler providerだけをregistryへ登録する。`guest_migration_composition.dart`とpresentation providerも同じcomposition rootを利用する。

## 4. 実施手順

### Stage 0: preflightとwire snapshot

1. 順序7のWordStatus、WordPage、Search、Ranking、Quiz、Sync、guest migration、DB testが成功することを確認する。
2. 旧direction feature、core datasource／DAO、direction DIの全importerを一覧化する。
3. Driftの2 tableについて`sqlite_master`、`PRAGMA table_info`、FK、index、schema versionをsnapshot化する。
4. Firebaseのcollection path、全field、bool encode、cursor queryをdirection別contract testで固定する。
5. `SyncDataset` stable ID、outbox mutation、checkpoint、registry順序をsnapshot化する。
6. sync handlerのsuccess、partial push failure、retry、dead-letter、stale ack、pending field保護、cursor、cancellationを共通characterization suiteへ整理する。
7. guest migrationのOR merge、mutation ID、transaction rollback、direction別countを固定する。

### Stage 1: direction別Drift infrastructureをWordStatusへ移す

1. 2つのDAO sourceを`word_status/internal/infrastructure/{esp_jpn,jpn_esp}/drift`へ移す。
2. 2つのlocal datasource interface／実装を同じdirection配下へ移す。
3. class renameを行う場合もmethod semantics、row型、SQL、transaction nestingを変更しない。
4. `part` pathを新source pathに合わせ、build runnerでDAO mixinを再生成する。
5. `core/di/data/data_di.dart`から2つのstatus DAO providerを除去する。
6. `JpnEspWordDao`の未使用status table import／accessor entryを削除して再生成する。
7. repository adapter、sync、guest migrationのtest importを新pathへ切り替える。
8. schema snapshotとlocal DAO contractを実行し、generated data class名とCREATE TABLE SQLが不変であることを確認する。

### Stage 2: Firebase infrastructureをWordStatusへ移す

1. direction別DTO、mapper、Firebase DAO、remote datasource interface／実装を各`firebase`配下へ移す。
2. DTOはdirection別wire型として維持し、共通domain entityへのconversionを追加しない。
3. collection／field定数値、document ID生成、bool encode、UTC変換を変更せず移植する。
4. remote queryの`updatedAt`＋document ID orderingとinclusive `startAt`を維持する。
5. mapper round-trip、missing optional metadata、full timestamp precisionをdirection別contract testへ移す。
6. Firestore emulator testが利用可能なら旧path fixtureを新実装でread／patchし、新collectionが作られないことを確認する。

### Stage 3: 共通sync algorithmとdirection adapterを追加する

1. internal `WordStatusSyncRecord`を追加し、両remote DTOからlosslessにmappingする。
2. `WordStatusDatasetAdapter`を追加し、local transaction、ack、remote patch／page、remote applyを抽象化する。
3. Esp-Jpn adapterを`espJpnWordStatus`へ固定し、Jpn-Esp adapterを`jpnEspWordStatus`へ固定する。
4. dataset mismatch、invalid decimal entity ID、remote mapping failureが別datasetへfallbackしないことをtestする。
5. `WordStatusDatasetSyncHandler`へ既存2 handlerの共通algorithmを一度だけ移植する。
6. 既存handlerと新handlerへ同じfake queue／remote／local contract suiteを通し、resultと副作用を比較する。
7. application repository adapterのlocal patch／outbox経路が同期handlerのremote apply経路と独立していることを確認する。

### Stage 4: production registryを新handlerへ切り替える

1. app compositionで2 direction adapterを構築する。
2. 同じhandler classからdataset別の2 instanceを構築する。
3. `DatasetHandlerRegistry`へ両instanceを従来どおり登録する。
4. account A／Bとdataset A／Bのqueue、checkpoint、pending fieldが混在しないintegration testを実行する。
5. session切替／cancel時にold epochがどちらのhandlerでもcancel resultになることを確認する。
6. production切替後、旧`EspJpnWordStatusSyncHandler`／`JpnEspWordStatusSyncHandler`を削除する。

### Stage 5: guest migrationをWordStatus capabilityへ切り替える

1. `WordStatusGuestMigration` portとdirection非依存のcount resultを追加する。
2. internal実装へ2 directionのOR merge、guest delete、outbox enqueueを移す。
3. `DetectGuestDataUseCase`から方向別local datasource importを除去する。
4. `MigrateGuestDataUseCase`から2つのprivate WordStatus migration methodと`CatalogId -> SyncDataset`相当の知識を除去する。
5. 外側の全dataset transaction、migration ID、session fence、処理順を維持する。
6. 片方のstatus migration失敗、後続MyWord失敗、session変更で両directionのrowとoutboxがrollbackすることをtestする。
7. guest data summaryのEsp-Jpn／Jpn-Esp countが従来と一致することを確認する。

### Stage 6: compositionとproviderを収束させる

1. WordStatus local／remote／dataset adapter、repository、handler、guest migration providerをapp bootstrapで構築する。
2. `word_status_composition.dart`と`sync_composition.dart`のdependency cycleを小さいshared provider moduleへの抽出で解消する。
3. `sync_composition.dart`から旧direction DI importを除去する。
4. `guest_migration_composition.dart`から旧direction DI importを除去する。
5. presentation用repository providerも同じlocal store instanceを利用するよう結線する。
6. ProviderContainerごとのDatabase／Firestore／handler isolationとdisposeをtestする。

### Stage 7: 旧graphを削除する

1. `features/esp_jpn_word_status/**`を削除する。
2. `features/jpn_esp_word_status/**`を削除する。

5. `core/di/data/data_di.dart`の旧DAO providerと旧importを削除する。
6. old class名、provider名、path、direction sync handler名の参照が0件であることを確認する。
7. table宣言、DatabaseProvider registration、migration SQL、Rankingのread-only table参照はschema bridgeとして残す。

### Stage 8: regressionとboundary確認

1. WordStatus domain／application／repository adapter／presentation testを実行する。
2. direction別Drift DAO／local store contract testを実行する。
3. direction別Firebase mapper／DAO／remote store contract testを実行する。
4. 共通sync handler contractを両dataset adapterへ実行する。
5. SyncEngine registry、scheduler、session cancellation testを実行する。
6. guest detection／migration／rollback testを実行する。
7. Ranking、Catalog、WordPage、Search、Quiz regressionを実行する。
8. DB schema／全migration path／Web seeder testを実行する。
9. build runnerを二回実行し、二回目にgenerated差分がないことを確認する。
10. `flutter analyze`、format、boundary検査、`git diff --check`を実行する。

## 7. リスクと対策

### 共通sync handlerがdirection差を消してしまう

共通handlerには制御algorithmだけを置き、dataset、DTO mapping、local store、remote collectionをdirection adapterへ残す。両adapterへ同じcontract suiteを通しつつ、既知の`>=`／`>`差を明示的fixtureとして固定する。

### table宣言移動でRanking／CatalogがWordStatus internalへ依存する

DAO／datasourceのowner移動とDart table declarationの物理移動を分離する。Catalogの未使用依存は除去し、Rankingがread projectionを切り替える順序9まではtable宣言をshared database runtimeへ残す。新しいinternal import例外は作らない。

### generated codeのpath変更で古いmixinが残る

sourceを移して`part` pathを更新後、build runnerで再生成する。旧generated path参照を`rg`で0件にし、二回目生成がcleanであることを完了条件にする。generated data class名はschema contractとして維持する。

### Firebase DTO統合でcollection／fieldが混線する

DTO／mapper／DAOはdirection別の明示実装として残し、共通化しない。collection path、identity field、bool encodeをsnapshot testで比較し、fallback collectionを持たせない。

### handler切替で既存queue／checkpointを読めなくなる

adapterのdatasetは既存`SyncDataset` enum caseそのものを返す。stable IDの新定数、enum rename、index利用、checkpoint namespace変更を禁止し、移行前に作ったqueue／checkpoint fixtureを新handlerで処理するtestを追加する。

### acknowledgementとqueue ackのatomicityが崩れる

共通handlerへの移植時もdirection local adapterのtransaction内でmetadata CASとqueue ackを行う。片方だけ成功するfailure injection testを残し、stale local revisionではackしないことを確認する。

### pending local fieldをremote pullが上書きする

pending field setはaccount＋dataset＋entityごとに構築する。datasetを外した共通cacheを作らず、同じword IDが両datasetに存在するcaseをtestする。

### composition root間でRiverpod import cycleが生じる

database、queue、checkpoint、outbox、execution guardのshared providerを依存の小さいbootstrap moduleへ抽出する。WordStatus compositionがsync engine registryをimportしない方向にし、`flutter analyze`でcycle／undefined providerを検出する。

### guest migrationの全体transactionが分割される

WordStatus capability内部で独立transactionを開始せず、外側の`DatabaseProvider.transaction`へ参加する。WordStatus後のMyWord失敗とsession fence failureを注入し、両status tableとoutboxがすべてrollbackすることを確認する。

### public migration portへpersistence詳細が漏れる

portはcountとmigrate capabilityだけを公開し、Drift row、Firebase DTO、`SyncDataset`、revision操作を型として返さない。内部adapterがmutation ID suffixとdataset mappingを所有する。

### 旧direction directoryがcompatibility layerとして残る

import置換後に旧directoryを一括削除し、export／typedef／delegating providerを残さない。旧pathとclass名の0件検査をCI前の完了条件にする。
