# 移行順序2: `CatalogId`・`CatalogWordRef`を定義する

- 状態: 実施前
- 対象: [`concept.md`](./concept.md) の「移行順」2
- 前提: [ADR 0001](../architecture/decisions/0001-catalog-word-status-my-word-ownership.md) が`Accepted`
- 成果物の性質: Catalog public identity contractの追加
- DB／Firebase／同期protocol変更: なし

## 1. 目的

Catalog wordをfeature横断で指すための唯一の公開identityとして、Catalog-ownedの`CatalogId`と`CatalogWordRef`を追加する。

このスライスでは新しいidentityを定義し、値としての不変条件、比較、安定した文字列表現を確定する。一方、既存の`WordType`、`SearchDirection`、`DictionaryDirection`や`int wordId`を利用しているroute／consumerはまだ置換しない。新旧identityを同時に広範囲へ反映すると、route互換性、WordStatus統合、Catalog port導入の障害を同じ変更で扱うことになるためである。

## 2. このスライスで固定する契約

### 2.1 配置と公開範囲

次の2ファイルをCatalogの公開contractとして追加する。

```text
lib/features/catalog/
└── port/
    ├── catalog_id.dart
    └── catalog_word_ref.dart
```

両ファイルはFlutter、Riverpod、Drift、Firebase、既存Catalog entity、consumer固有enumに依存しないpure Dartとする。`port`から`internal`または他featureをimportしてはならない。

### 2.2 `CatalogId`

初期variantは、現在の2つの辞書masterに一対一で対応させる。

```dart
enum CatalogId {
  espJpnMain('esp-jpn-main'),
  jpnEspMain('jpn-esp-main');

  const CatalogId(this.wireValue);
  final String wireValue;

  static CatalogId? tryParse(String value) { ... }
}
```

決定事項:

- enum名ではなく明示的な`wireValue`を永続的な外部表現とする。
- `wireValue`は既存`WordType.name`や`SyncDataset`の値を流用しない。
- `tryParse`は未知値を例外にせず`null`で返す。どのerrorへ変換するかはroute／adapter側が決める。
- `espEng`／`engEsp`は現在Catalog実装がなく、word detailでもunsupportedなので追加しない。
- language directionではなくcatalog datasetのidentityとする。同じ方向に別Catalogが増えた場合は別variantを追加できる。

### 2.3 `CatalogWordRef`

```dart
final class CatalogWordRef {
  const CatalogWordRef({
    required this.catalogId,
    required this.wordId,
  }) : assert(wordId > 0);

  final CatalogId catalogId;
  final int wordId;

  @override
  bool operator ==(Object other) { ... }

  @override
  int get hashCode => Object.hash(catalogId, wordId);
}
```

決定事項:

- identityは`CatalogId × positive int wordId`とする。
- `wordId`は既存Drift schemaとRepository契約を保つため`int`のままにする。
- immutable valueとしてvalue equalityと`hashCode`を実装し、provider family keyやMap keyに安全に使えるようにする。
- `toString`はdiagnostic用途に限定する。route、DB、syncのserialization contractとして利用しない。
- 内部entity、見出し語、`hasConj`、status、account IDを含めない。
- JSON codecやroute parameter変換は追加しない。route用codecは移行順序5で既存deep link互換を含めて決める。

`assert`だけではrelease buildの外部入力検証にならない。外部文字列から生成するroute／Firebase／DB adapterは、`CatalogWordRef`を構築する前に`wordId > 0`を検証する。通常のtyped codeから不正値が渡された場合を即座に検出するため、constructorにもassertを置く。

## 3. 既存identity表現の棚卸し

| 現在の型／値 | owner | 現在の用途 | 後続の変換境界 |
|---|---|---|---|
| `WordType` | legacy `core`／routing | word detail routeと画面分岐。未対応の`espEng`／`engEsp`も含む | 移行順序5でapp routingが`CatalogId`へ変換 |
| `SearchDirection` | Search | 検索queryとSearch内の能力分岐 | Searchのquery adapterが結果の`CatalogWordRef`を構築。Search固有query型は必要な間残す |
| `DictionaryDirection` | WordStatus presentation | 方向別status実装の選択 | 移行順序7でWordStatus contractを`CatalogWordRef`へ変更 |
| raw `int wordId` | Repository／DAO／各consumer | 方向情報を別引数または暗黙知で補う | Catalog adapter内で`CatalogWordRef.wordId`へunwrap |
| `SyncDataset.*WordStatus` | Sync protocol | 物理datasetのstable ID | 変更しない。移行順序8のadapterが`CatalogId`と対応付ける |

重要な依存規則:

- Catalog側に`WordType`／`SearchDirection`／`DictionaryDirection`からの変換extensionを置かない。Catalogがconsumer型へ逆依存するためである。
- 変換は、そのlegacy型を所有するconsumerまたはapp composition boundaryに一つだけ置く。
- このスライスでは棚卸しとcontract testのみ行い、production consumer用mapperは必要になる後続スライスで追加する。

## 4. 実施手順

### Stage 0: preflight

1. ADR 0001が`Accepted`であり、Catalog identityのownerがCatalogと記載されていることを確認する。
2. `CatalogId`／`CatalogWordRef`相当の別実装が追加されていないことを検索する。
3. 作業開始時の差分を記録し、既存のユーザー変更を変更対象から除外する。

### Stage 1: `CatalogId`を追加

1. `catalog_id.dart`に2つのvariantと明示的`wireValue`を定義する。
2. `tryParse`を全variantの`wireValue`に対する逆変換として実装する。
3. enumの`.name`をserializationに使用しないことをdoc commentで固定する。

### Stage 2: `CatalogWordRef`を追加

1. `catalog_word_ref.dart`にimmutable final classを定義する。
2. positive IDのassert、value equality、`hashCode`、diagnostic `toString`を実装する。
3. `CatalogId`以外の方向型やCatalog内部entityをimportしていないことを確認する。

### Stage 3: contract testを追加

`test/unit/features/catalog/port/catalog_identity_test.dart`で次を検証する。

- 2つの`wireValue`が期待するstable文字列であり重複しない
- `tryParse`が既知値をround tripし、未知値とenum名の誤用をrejectする
- 同じ`catalogId`／`wordId`は等しく同じhashになる
- catalogまたはword IDが異なれば等しくない
- debug testで0以下のIDがassertion errorになる
- `Set<CatalogWordRef>`／`Map<CatalogWordRef, ...>`のkeyとしてvalue equalityが機能する

### Stage 4: identity inventoryを検証

検索結果をplanまたはtest commentの根拠として更新し、次の利用箇所が後続作業から漏れていないことを確認する。

- `app/routing/contracts/word_detail_route.dart`
- Searchのquery／result／presentation
- WordDetailのquery／load key／presentation
- Quiz game routeとCatalog conjugation取得
- Ranking card／status button
- 西日・日西WordStatusのapplication／DI
- guest migrationと方向別`SyncDataset`

このStageでは上記ファイルを編集しない。

## 7. リスクと対策

### enum名をwire formatとして固定してしまう

明示的な`wireValue`とround-trip testを置き、renameと外部表現を分離する。

### `CatalogId`をlanguage directionとして扱う

doc commentと命名をdataset identityに揃える。能力判定は`CatalogId`自体へboolean getterとして埋め込まず、Catalog adapterが担う。

### 移行途中にidentityの正本が複数になる

新規コードでCatalog wordをfeature間受け渡しするときだけ`CatalogWordRef`を採用し、legacy型との変換はconsumer boundaryへ限定する。既存型を新しい共通型へ改名して温存しない。

### validationとserializationを広げすぎる

この段階ではtyped identityと`CatalogId.wireValue`だけを固定する。route codec、JSON、DB column、sync payloadは各ownerの後続スライスで互換要件と一緒に扱う。

- Catalogのread port／DTO／legacy Repository adapter
- 既存`WordType`、`SearchDirection`、`DictionaryDirection`の削除または置換
- WordDetail route、path、query parameter、deep linkの変更
- Search／Quiz／Ranking／WordStatus consumerの移行
- `hasConj`のrouteからの除去
- DB／Firebase／sync serializationへの`CatalogId`追加
- Catalog entity／Repository／DAO／mapperの物理移動
- import boundary CI ruleの追加

## 10. 次の移行への引き継ぎ

移行順序3はこのidentityを入力に、Catalog公開read portと既存Repositoryへのadapterを追加する。開始条件は次の通り。

- `CatalogWordRef`のvalue semanticsとpositive ID invariantがtestで固定されている
- `CatalogId`のstable wire valueがenum名から独立している
- Catalogがconsumer固有direction型へ依存しない方針が維持されている
- 既存Repositoryとschemaを変更せず、adapterが`CatalogWordRef`をlegacy `int wordId`へ変換できる
