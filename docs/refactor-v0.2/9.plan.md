# 移行順序9: MyWord／JpnEspWordからStatusフィールドを除去しread projectionで合成する

- 状態: 実施前
- 対象: [`concept.md`](./concept.md) の「移行順」9
- 前提: [`8.plan.md`](./8.plan.md) のWordStatus infrastructure adapter化が実装・検証済み
- 成果物の性質: statusを持たないwrite entity、MyWord一覧用projection、Catalog identityとWordStatusを画面境界で合成するSearch／Ranking projection、明示されたread-only cross-feature query規則
- DB data migration: なし
- Drift schema version／table／column／PK／FK／index／asset DB変更: なし
- Firebase collection／document／field変更: なし
- `SyncDataset`／outbox payload／checkpoint変更: なし

## 1. 目的

`MyWord`と`JpnEspWord`の本体Entityから、別のlifecycleを持つStatusフィールドを除去する。

現状の物理schemaはすでに責務分離されている。

```text
MyWords                  MyWordStatus
  word／contents           isLearned／isBookmarked／hasNote

JpnEspWords              JpnEspWordStatus
  word                     isLearned／isBookmarked／hasNote
```

一方、Dartのwrite entityには古い合成結果が残っている。

```text
MyWord
  word／contents
  isLearned=false／isBookmarked=false   <- Repositoryが常にfalseを注入

JpnEspWord
  word
  isLearned=false／isBookmarked=false／hasNote=false
                                              <- mapperが値を供給しない
```

この状態では、型だけを見ると本体EntityがStatusを所有しているように見えるうえ、実データが存在しても常に`false`となる。順序9ではwrite modelを正し、画面に必要な合成値はread modelで扱う。

移行後の責務は次とする。

```text
MyWord command model            MyWordStatus command model
  create／edit／delete             toggle／sync／conflict
              \                  /
               MyWordItemProjection
                    -> MyWord list／card

CatalogWord／CatalogWordRef     WordStatus
  dictionary identity／content   account-scoped mutable state
              \                  /
       Search／Ranking／WordDetail read projection
```

辞書WordStatusとMyWordStatusは統合しない。共通化するのは、別ownerのread結果を画面用projectionで合成する設計原則だけである。

## 2. 移行前に固定するcontract

### 2.1 MyWord本体contract

- `MyWords` tableは`my_word_id`、`word`、`contents`、`edit_at`、account scope、sync metadataだけを保持する。
- `MyWord`の作成・更新・削除payloadは`word`／`contents`／`deletedAt`だけを対象とする。
- `SyncDataset.myWords`と`SyncDataset.myWordStatus`は別datasetのままとする。
- MyWord削除時は同一accountのMyWordStatusを削除し、本体はtombstone化する現行順序を維持する。
- MyWordStatusの同期順序制約`myWordStatus -> myWords`を維持する。
- guest scopeは`legacy_unowned`、signed-in scopeはcurrent account IDを用い、別accountのStatusを合成しない。

`MyWord.isLearned`と`MyWord.isBookmarked`は永続化値ではなく、`MyWordRepository._toEntity`が常に`false`を設定する互換用フィールドである。削除前characterization testでこの事実を固定し、削除後は同じ偽値を別の本体フィールドとして残さない。

### 2.2 MyWordStatus contract

- Statusのownerは引き続き`features/my_word`内のMyWordStatus domain／repository／syncである。
- IDはUUID文字列、scope keyは`(account_id, my_word_id)`を維持する。
- missing rowは表示上`false／false／false`として扱うが、readのためだけにrowをinsertしない。
- toggle、local revision、outbox enqueue、remote acknowledgement、pending field保護を変更しない。
- `hasNote`の現行UI差を本スライスで解消しない。
- Status更新はMyWord本体の`editAt`、`localRevision`、outboxを更新しない。

### 2.3 JpnEspWord／Catalog contract

- `JpnEspWords` tableは`jpn_esp_word_id`と`word`だけを保持する。
- `JpnEspWord`はCatalog内部のread-only dictionary entityであり、ユーザー状態を所有しない。
- `CatalogDriftMapper.jpnEspWord`はword IDとheadwordだけをmappingする。
- 辞書Statusのidentityは`CatalogWordRef(CatalogId.jpnEspMain, wordId)`を用いる。
- Esp-Jpn／Jpn-EspのStatusは共通`WordStatus` domainを使うが、物理table、collection、datasetは順序8のまま分離する。

### 2.4 Search表示contract

- 検索条件、direction判定、page／size、primary result順序を変更しない。
- meaning、ranking、star、conjugationの部分失敗と`QueryIssue` contractを変更しない。
- Search resultの辞書identityは`CatalogWordRef`へ一意に変換できる。
- Search cardのStatus表示／toggleは、そのidentityを使うWordStatus query／commandだけをsource of truthとする。
- Statusを取得できない場合は既存どおり未選択表示にfallbackし、primary search自体を失敗させない。
- `CardView.isLearned`／`isBookmarked`は現在描画に使われず、`DictionaryStatusButtons`が実値をwatchしている。このdead inputをprojection contractとして残さない。

### 2.5 Ranking query contract

- status include／exclude filterはpagination前にSQLへ適用する。
- filterはcurrent accountまたはguest scopeだけを参照する。
- missing Status rowは全Status tagがfalseとして扱われる。
- include tagsは現行どおり同一row内のOR、exclude tagsはその条件を満たすrowの`NOT EXISTS`とする。
- rank順、`multiLemma` grouping、look-ahead一件、`LIMIT／OFFSET` semanticsを維持する。
- Ranking cardのStatus buttonは`CatalogWordRef(CatalogId.espJpnMain, wordId)`を使うlive WordStatus projectionをsource of truthとする。

`FeatureTag.myWord`が現行`word_status.my_word`を参照する一方、現在の`word_status` tableに`my_word` columnは存在しない。この不整合は実装前preflightで再現testを作り、順序9で次のどちらかに確定する。

1. product上不要ならfilter選択肢と`FeatureTag.myWord`のRanking mappingを削除する。
2. product上必要ならMyWordとの関係を定義した別のread model／tableを設計する。

存在しないcolumnをStatus fieldとして復活させること、または意味を推測して常にfalseへ置換することは禁止する。後者の新仕様が必要なら本計画とは別のproduct decisionとする。

## 3. 設計方針

### 3.1 write entityとread projectionを型で分ける

write側の最終形を次とする。

```dart
class MyWord {
  final String wordId;
  final String word;
  final String contents;
  final DateTime editAt;
}

class JpnEspWord {
  final int id;
  final String word;
}
```

`copyWith`からもStatus parameterを除去する。deprecated field、extension getter、常にfalseを返すcompatibility accessorは残さない。

画面用には別型を用意する。

```dart
final class MyWordItemProjection {
  final MyWord word;
  final MyWordStatus status;
}
```

実際の命名は既存query model規約へ合わせてよいが、domain write entityを継承せず、Statusを`copyWith`で本体へ戻さないことを必須とする。

### 3.2 MyWord listは一つのreactive projectionで合成する

現在の一覧はIDごとにMyWord streamとMyWordStatus streamを別々にwatchし、widgetで組み合わせている。順序9ではread専用portを追加し、合成責任を明示する。

```dart
abstract interface class MyWordItemQueryRepository {
  Stream<MyWordItemProjection> watchItem(
    String myWordId, {
    required String accountId,
  });
}
```

Drift実装は`MyWords LEFT JOIN MyWordStatus`を`account_id`と`my_word_id`の両方で結合する。次を守る。

- `MyWords.deleted_at IS NULL`だけを表示する。
- Status側の`deleted_at`も表示対象外とする。
- Status rowがなければ`MyWordStatus`の3値をfalseで構築する。
- account conditionをJOIN条件とWHERE条件の双方で取り違えない。
- read queryはrowを作成せず、outboxへ書かない。
- MyWordまたはMyWordStatusの変更で同じprojection streamが再emitされる。
- `.distinct()`はprojectionの全表示値で比較し、Status toggleを落とさない。

paginationは本スライスでは既存のID page取得を維持してよい。各cardの二つのwatchを一つのprojection watchへ置換し、ページング挙動とlive updateを同時に変えない。

query portとprojection modelは`features/my_word/application/query`へ置き、Drift row／DAO／Riverpodを公開しない。create／update／delete repositoryとStatus command repositoryは変更しない。

### 3.3 Catalog entityへStatusを戻さない

Search／Ranking／WordDetailがStatusを必要とするときは、`JpnEspWord`やCatalog entityへbooleanを埋め戻さず、`CatalogWordRef`をjoin keyとして使う。

Search resultは次のいずれかでidentityを一度だけ持つ。

- 推奨: `SearchResultItem`が`CatalogWordRef word`を持つ。
- 互換的移行: `wordId`と`direction`からmapperで`CatalogWordRef`を作り、presentation内の一か所だけで保持する。

最終的にcard、route、WordStatus queryへ別々のswitch文でdirectionを変換しない。`CatalogId`変換はSearch query adapterまたはprojection mapperの一か所に集約する。

Search／RankingのStatus buttonはlive `DictionaryStatusButtons`を利用しており、page取得時点のStatus snapshotを`SearchResultItem`／`RankingListItem`へ重複保持しない。静的page projectionとreactive Status projectionをcard境界で合成する。

```text
SearchResultItem／RankingListItem
  + CatalogWordRef
  + WordStatusState (reactive)
  -> card projection
```

これによりtoggle直後の表示を再検索／再ページングなしで更新できる。

### 3.4 Rankingのcross-feature JOINはRanking-owned read adapterに置く

Ranking filterはStatus条件をpagination後に適用できない。batch enrichmentで後から除外すると、page size、offset、hasNextが壊れる。このため`RankingDao`のread-only `EXISTS` queryはRanking-owned projection adapterとして維持する。

許可する依存は次である。

```text
Ranking application query port
  <- Ranking data read adapter
       -> shared Drift schema declarations
       -> Catalog／WordStatus tablesをread-only JOIN／EXISTS
```

禁止する依存は次である。

- Rankingから`features/word_status/internal`へのimport。
- RankingからWordStatus DAO／local store／sync adapterの呼び出し。
- Ranking query内でStatus tableへinsert／update／deleteすること。
- WordStatus domainからRankingのfilter enumを参照すること。
- status filterをpage取得後のDart処理へ移すこと。

`EspJpnWordStatus` table declarationは順序8から続くshared schema bridgeとして本スライスでも利用する。業務ownerをRankingや`core`へ戻す判断ではない。最終物理配置は順序11で決める。

### 3.5 SearchのStatusは部分失敗境界を分離する

Search primary queryはCatalog dataの取得であり、Status read failureで検索全体を失敗させない。Status buttonが個別にwatchする現在の境界を維持し、次を整理する。

- `CardView`から未使用の`isLearned`／`isBookmarked` constructor fieldを削除する。
- `statusWord`をnon-null `CatalogWordRef`とし、辞書cardでは必ず一意のidentityを渡す。
- conjugation suggestionも元のEsp-Jpn `CatalogWordRef`を利用する。
- Jpn-Esp cardが`JpnEspWord`のdefault falseへ依存しないことをtestする。
- Status read error／loading／missing rowの表示はWordStatus presentation contractへ委譲する。

Search query resultにStatus snapshotを追加する場合でも、それをtoggle UIのsource of truthにしてはならない。snapshotがfilter／sort要件として必要になるまでは重複取得を避ける。

### 3.6 command境界は変更しない

projection導入後も更新経路は分離する。

```text
MyWordItemProjection
  word edit/delete -> MyWordCommand
  status toggle    -> MyWordStatusCommand

Dictionary card projection
  navigation       -> Search／Ranking route
  status toggle    -> UpdateWordStatus
```

projection repositoryへ`save`、`toggle`、`delete`を追加しない。read modelをwrite modelへ渡して一括保存しない。

- `my_words`、`my_word_status`、`jpn_esp_words`、`jpn_esp_word_status`、`word_status`のCREATE TABLE SQLが移行前snapshotと一致する。
- MyWordとMyWordStatusのFirebase collection path／fieldが一致する。
- Jpn-Esp WordStatusとEsp-Jpn WordStatusのFirebase path／fieldが一致する。
- `my_words` outbox payloadにStatus fieldが追加されていない。
- `my_word_status` outbox payloadとfield maskが変更されていない。
- dictionary WordStatusの2 dataset stable IDが変更されていない。
- guest migrationのrow count、OR merge、mutation ID、rollbackが変更されていない。
- MyWord projectionがaccount Aのwordとaccount BのStatusを結合しない。
- Ranking filterがpage境界を跨いでもStatus条件を満たす件数と`hasNext`を返す。

## 7. リスクと対策

### Entity field削除で隠れたUI依存が壊れる

constructorだけでなくgetter、`copyWith`、fake、legacy modalをpreflightで列挙する。削除前に利用中widgetと未到達legacy widgetを分け、利用中箇所はprojectionへ切り替えてからfieldを削除する。

### MyWord projectionが別accountのStatusを結合する

JOIN keyを`my_word_id`だけにせず`account_id`も必須にする。同じUUIDをguest、account A、account Bへ置くtestを追加し、query引数にaccount scopeを必須化する。

### missing Status rowのreadが書込みを発生させる

LEFT JOIN結果をin-memoryのdefault `MyWordStatus`へmappingするだけにし、insert-on-readを禁止する。read後にtable row countとoutbox countが変化しないtestを追加する。

### 二つのstreamを一つへ変えてStatus toggleが再描画されない

projection DAOの`readsFrom`／watch dependencyにMyWordsとMyWordStatusの両方を含める。Statusだけを更新するtestで新しいprojectionがemitされ、word値は不変であることを確認する。

### Search resultへStatus snapshotを入れてlive stateと競合する

toggle UIのsource of truthは`DictionaryStatusButtons`のWordStatus watchに限定する。page itemにはidentityだけを渡し、boolean snapshotを重複保持しない。

### direction変換の重複でJpn-Esp StatusをEsp-Jpnへ書く

Search direction→`CatalogId` mappingを一か所へ集約し、同じnumeric word IDを両Catalogへ用意したrouting testを追加する。fallback Catalogを設けない。

### Ranking filterを後処理に移してpaginationが壊れる

Status filterをRanking DAOのSQL `EXISTS`に残し、filter後に`ORDER BY／LIMIT／OFFSET`する。複数pageとlook-aheadを含むintegration testで固定する。

### RankingからWordStatus internalへの依存が生まれる

Rankingはshared schema declarationだけをread-only queryで参照する。WordStatus DAO／adapterをimportしない。これは順序10のboundary ruleとして自動化する。

### `FeatureTag.myWord`の存在しないcolumn問題を偽装する

preflight testで現状を可視化し、product上の意味を確定するまでStatus tableにcolumnを追加しない。削除または別projectionという明示的判断だけを受け入れる。

### schema変更を伴う作業へ膨らむ

本体tableはすでにStatus列を持たないため、Dart entity／read adapterだけを変更する。schema version、migration、Firebase、SyncDatasetに差分が出た場合は本スライスを停止して別migrationとして扱う。

## 10. 次の移行への引き継ぎ

移行順序10では、順序9で確定したownerとread-side例外をbaselineなし・違反0のCI ruleとして固定する。

- `MyWord`／Catalog word entityへ`isLearned`、`isBookmarked`、`hasNote`を再追加しない。
- Search／Ranking／MyWord query projectionからwriteしない。
- `features/word_status`外から`features/word_status/internal`をimportしない。
- Rankingのcross-feature SQLはread-only projection adapterに限定する。
- Search／RankingからWordStatus DAO、Firebase DTO、sync adapter、`SyncDataset`を参照しない。
- MyWord projectionのJOINには`account_id`を必須とする。
- `CardView`等へ常時falseのStatus booleanを再追加しない。

移行順序11では、Rankingのread-only projectionを維持したまま、shared database runtimeに残るWordStatus table declarationとgenerated schemaの最終配置を決める。物理配置を変えても、Ranking query port、Status filter semantics、table名、column名は変更しない。

またMyWordの最終directory整理では、command repository、Status command repository、query projection repositoryを役割別に配置する。projectionが便利であることを理由にwrite modelやsync modelを再統合しない。
