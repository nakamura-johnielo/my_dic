# 移行順序6: `core`のWord／Dictionary／ConjugationをCatalogへ移す

- 状態: 実施前
- 対象: [`concept.md`](./concept.md) の「移行順」6
- 前提: [`5.plan.md`](./5.plan.md) の`hasConj`除去とWordDetailのCatalog port切替が実装・検証済み
- 成果物の性質: Catalog ownershipの物理反映、legacy seamの撤去、consumer依存の再結線
- DB／Firebase／同期protocol変更: なし
- route／画面仕様変更: なし
- Drift schema version／table名／column名／asset DB変更: なし

## 1. 目的

辞書Catalogの業務概念とread実装を`core`から`features/catalog/internal`へ移し、[`ADR 0001`](../architecture/decisions/0001-catalog-word-status-my-word-ownership.md)で決定した論理ownershipを物理配置と依存方向へ反映する。

移行前は、Catalog公開portが存在していても実体は次のlegacy graphに依存している。

```text
WordDetail / Quiz candidate
  -> Catalog port / consumer-owned port
  -> catalog/internal/infrastructure/legacy adapter
  -> core Repository port
  -> core Repository implementation
  -> core datasource -> core DAO -> shared Drift database

Search
  -> Search-owned repository
  -> core Catalog datasource / converter

Quiz game
  -> core fetch_conjugation use case
  -> core Conjugation Repository
```

移行後は次へ統一する。

```text
WordDetail / Quiz game
  -> Catalog port
  -> catalog/internal Drift reader
  -> Catalog datasource / DAO -> shared Drift database runtime

Search / Quiz candidate
  -> consumer-owned port
  <- catalog/internal provider-side adapter
  -> Catalog datasource / DAO -> shared Drift database runtime
```

完了時、`core`はResult／Error、logger、共有DB runtimeなどの技術基盤だけを保持する。Word、DictionaryEntry、Example、Idiom、Supplement、品詞、スペイン語活用のentity、Repository、datasource、DAO、mapper、Catalog用DIはCatalog internalの所有になる。

このスライスは「ファイルを移してimportを書き換える」作業ではない。外部featureがCatalog internalへ直接依存しないseamを先に完成させ、legacy graphを参照するconsumerが0件になってから旧`core`実装を削除する。

## 2. 現行contractのcharacterization

実装前に次をtestで固定する。

| 項目 | 維持するcontract |
|---|---|
| Catalog identity | `CatalogWordRef(CatalogId, positive wordId)` |
| Esp→Jpn detail | dictionary、example、idiom、supplementの順序・nullability・HTML文字列を維持 |
| Jpn→Esp detail | dictionary、exampleの順序・nullability・HTML文字列を維持 |
| conjugation detail | mood／tense／subject、participles、欠損値の表現を維持 |
| unsupported能力 | Jpn→Esp conjugationはDBへ問い合わせず`BusinessRuleError` |
| repository failure | 既存の`AppError`種別、message、部分失敗の扱いを維持 |
| Search primary | 方向、順序、0-based page、page size、`hasNext`を維持 |
| Search suggestion | Esp→Jpnかつpage 0だけ、最大4件、matchesとenrichmentを維持 |
| Quiz candidate | primary順序、page、meaning／ranking／star count warningを維持 |
| Quiz game | 出題対象の活用、カード順、英語活用合成、失敗時の表示を維持 |
| Drift schema | schema version、table／column／PK／FK／index、generated data class名を維持 |
| asset／seed | DB asset名、Web seeding、native copy、migration処理を維持 |

特に、同じfixtureを旧converterと新Catalog mapperへ入力し、公開`CatalogEntryDetail`／`CatalogConjugation`が同値になるgolden-style contract testを追加する。移動と同時にnullを空文字へ変える、List順をsortする、HTMLをplain text化するなどの意味変更を行わない。

## 3. 設計方針

### 3.1 Catalogは`port`と`internal`の二層を維持する

目標配置は次を基本とする。実装時に既存symbolへ合わせてファイル名を調整してよいが、外部公開範囲は増やさない。

```text
lib/features/catalog/
├── port/
│   ├── catalog_id.dart
│   ├── catalog_word_ref.dart
│   ├── catalog_reader.dart
│   ├── conjugation_reader.dart
│   └── model/**
└── internal/
    ├── domain/
    │   ├── word/**
    │   ├── dictionary_entry/**
    │   ├── example/**
    │   ├── conjugation/**
    │   └── repository/**
    └── infrastructure/
        ├── drift/
        │   ├── dao/esp_jpn/**
        │   ├── dao/jpn_esp/**
        │   ├── datasource/esp_jpn/**
        │   ├── datasource/jpn_esp/**
        │   ├── mapper/**
        │   └── repository/**
        └── integration/
            ├── search/**
            └── quiz_candidate/**
```

- `port`はCatalog外からimport可能な唯一の領域とする。
- internal entityやDrift rowを`port` DTOのfieldへ入れない。
- Catalog public readerへSearch pagination、Ranking filter、Quiz ruleを追加しない。
- consumer固有queryはconsumerがportを所有し、Catalog internalのintegration adapterが実装する。
- internalのRepository abstractionを残す場合もCatalog内部限定とし、appや他featureへproviderを公開しない。

### 3.2 Catalog語彙とconsumer表示語彙を分離する

現在の`core/shared/enums/word/part_of_speech.dart`と`core/shared/enums/conjugacion/**`には、Catalog taxonomy、DB column名、UI日本語label、Quiz英語変換が混在している。ディレクトリだけCatalogへ移すと、外部featureがinternalをimportするか、CatalogがQuiz表示都合を所有することになる。

この段階で次へ分ける。

- Catalog公開契約: `CatalogPartOfSpeech`、既存`CatalogMoodTense`、`CatalogSubject`
- Catalog internal persistence mapping: DB文字列／columnとの変換
- Search／Ranking presentation: 日本語labelやfilter表示extension
- Quiz: `EnglishMoodTense`、`EnglishSubject`、英語文生成用mapping

`PartOfSpeech.name`や現行`display`をSQL／fixtureが利用している箇所はcharacterization testでwire valueを固定する。enum renameでDB query文字列を変えない。

`MoodTenseSubject`はSearchのmatch位置を表す必要があるため、Catalog internal enumを漏らさず、Search-ownedのmatch keyへmapperで変換する。Catalog public `CatalogConjugation`は既存の`CatalogMoodTense`／`CatalogSubject`を維持する。

### 3.3 SearchはCatalog internal datasourceをimportしない

現在の`SearchQueryDao`と`DriftSearchQueryRepository`は`core`にある方向別word／dictionary／conjugation datasourceとconverterを直接importしている。移動後にimport先だけを`features/catalog/internal`へ変えることは禁止する。

Searchの既存`ISearchQueryRepository`をconsumer-owned portとして維持し、現行のDrift query／enrichment実装をprovider-side integration adapterとしてCatalog internalへ移す。

```text
Search application -> ISearchQueryRepository
                         ^
                         |
app composition -> Catalog internal Search adapter
                         |
                   Catalog datasource / shared DB
```

- Search query、result、issue、directionはSearch所有のままにする。
- adapterがSearch application portをimportするのはdependency inversionの実装点として許可する。
- Catalog domain、Catalog public port、Catalog readerはSearch型をimportしない。
- ranking enrichmentのread-only queryは現行結果を維持し、Catalog汎用readerへ追加しない。
- Search presentation／DIからCatalog internal具象型を参照しない。

### 3.4 Quiz candidateとQuiz gameを別経路で扱う

Quiz candidateは順序4で追加した`QuizCandidateSource`を維持する。`legacy_quiz_candidate_*`は新Catalog datasourceへ接続後、`drift_quiz_candidate_*`など実体を表すneutral nameへ変更する。`getQuizConjugacionByWordWithPage`というconsumer名を持つCatalog datasource methodは、`searchConjugations`等のneutralな内部queryへ変更し、Quiz ruleはadapterへ残す。

Quiz gameは現在の`IFetchEspConjugationUseCase`と`EspConjugacions`を廃止し、`ConjugationReader.getConjugation(CatalogWordRef)`へ切り替える。

- Quiz routeのraw `wordId`はDI／view model境界で`CatalogId.espJpnMain`の`CatalogWordRef`へ変換する。
- view modelとwidgetは`CatalogConjugation`またはQuiz-owned immutable projectionだけを使う。
- `CatalogMoodTense`／`CatalogSubject`からQuiz表示・英語変換へのmappingはQuiz側に置く。
- `ConjugationReader` failure時に現行どおりquiz画面を破壊せず、空／取得不能として扱う挙動を維持する。
- 英語活用用`EsEnConjugacions`、そのRepository、DAOはQuiz所有の別datasetであり、Catalogのスペイン語活用と統合しない。

### 3.5 `legacy` adapterは新実装へ置換してから削除する

順序3で追加した`LegacyCatalogReaderAdapter`／`LegacyConjugationReaderAdapter`／`LegacyCatalogMapper`はanti-corruption layerであり、恒久実装ではない。

新Catalog infrastructureが完成した後、次のいずれかへ置換する。

1. Catalog internal Repositoryを維持し、`DriftCatalogReader`がRepository結果をpublic DTOへmapする。
2. read-only用途だけなら`DriftCatalogReader`／`DriftConjugationReader`がdatasourceを直接利用する。

実装時は不要なlayerを増やさない方を選べる。ただしpublic readerのerror semantics、DTO mapping、test seamは維持する。composition完了後、class名／directory／test名から`legacy`を除去し、旧core Repository providerを経由しないことを完了条件とする。

### 3.6 shared Drift database runtimeとschemaを移動対象から分離する

`DatabaseProvider`はCatalog、WordStatus、MyWord、Sync、Ranking、Quizが共有する物理databaseのcomposition rootであるため、この段階では`core/infrastructure/database/drift`に残す。

また、Driftの単一database code generationと既存WordStatus FKを壊さないため、table宣言とgenerated `database_provider.g.dart`は本スライスではdatabase runtimeのschema ABIとして現配置を維持してよい。移す対象はCatalogのquery／write責務を持つDAOであり、table宣言の物理整理は移行順序11で全feature registration方式と合わせて判断する。

これはtableの業務ownershipを`core`へ戻す決定ではない。Catalog tableに対するschema変更判断はCatalog ownerが持つが、今回の完了判定は次とする。

- `core/domain/**`にCatalog業務entity／Repositoryが0件
- `core/application/**`にCatalog fetch use caseが0件
- `core/infrastructure/repositories/**`にCatalog Repository／mapperが0件
- `core/infrastructure/datasource/{esj,jpn_esp,conjugacion}`が0件
- Catalog用DAOがCatalog internalへ移動済み
- `DatabaseProvider`、table宣言、migration、schema versionは同一

WordStatus DAO／datasource、status table、Firebase、SyncDatasetは順序7〜8の対象なので移動しない。Catalog DAOと同じdirectoryに混在している場合でも、status関連fileを機械的に一緒に移さない。

### 3.7 code generationは一つの独立stageとして扱う

DAO移動で`part` pathと`lib/__generated/**`の出力先が変わる。手作業でgenerated fileを編集せず、source file移動後にbuild runnerで再生成する。

- 旧DAOのgenerated fileが参照されていないことを確認して削除する。
- `DatabaseProvider`のgenerated data class名は維持する。
- schema snapshot／migration testでCREATE TABLE SQLが変わっていないことを確認する。
- generated diffとsource diffを分けてレビューできるよう、DAO移動stageでは業務ロジック変更を行わない。

## 4. 実施手順

### Stage 0: preflightとcharacterization

1. 順序3〜5のCatalog port、WordDetail、Quiz candidate、route testと`flutter analyze`が成功することを確認する。
2. core Catalog entity／Repository／datasource／converter／DAOのimporterを`rg`で一覧化し、consumerごとの切替先を表にする。
3. direction別dictionary、conjugation、Search、Quiz gameの現行fixtureとfailure semanticsをtestで固定する。
4. schema version、table／column／FK／index、generated data class名をschema testでsnapshot化する。
5. `core/shared/enums`のwire value、DB文字列、UI label、英語変換の利用箇所を分離して記録する。

### Stage 1: 公開contractの不足を補う

1. Catalog portに`CatalogPartOfSpeech`とstableなwire valueを追加する。
2. Search-owned conjugation match keyを追加し、Catalog internal型を公開しない形を固定する。
3. Quiz gameが`CatalogConjugation`を受け取れるQuiz-owned mapper／projectionをadditiveに追加する。
4. public contractのcollection immutability、enum変換、unknown DB valueの扱いをtestする。
5. Catalog portがFlutter、Riverpod、Drift、core domain、他featureをimportしていないことを確認する。

### Stage 2: Catalog domainと内部Repository portを移す

1. Word、direction別dictionary entry、example、idiom、supplement、conjugation entityを`catalog/internal/domain`へ移す。
2. direction別word／dictionary／conjugation Repository interfaceを`catalog/internal/domain/repository`へ移す。
3. `flutter/foundation.dart`の`@immutable`だけのための依存は、必要なら純Dartのimmutable設計へ置換する。
4. internal entityのList／Mapが外部変更可能だった箇所は挙動変更を避けて移し、immutability改善はpublic DTO境界だけで保証する。
5. domain testをCatalog配下へ移し、Catalog domainがFlutter、Riverpod、Drift、consumer featureをimportしないことを確認する。

### Stage 3: mapper／Repository／datasource／DAOを移す

1. direction別converterをCatalog internal mapperへ移し、DB row→internal entityとinternal entity→public DTOの責務を分ける。
2. direction別Repository実装をCatalog internalへ移す。
3. `esj`、`jpn_esp`、`conjugacion` datasource interface／実装をCatalog internalへ移す。
4. dictionary、word、example、idiom、supplement、part-of-speech、Spanish conjugation DAOをCatalog internalへ移す。
5. DAOのSQL、sort、limit／offset、null fallback、`readsFrom`を変更せず移植する。
6. `getQuiz...`等のconsumer名を持つ内部APIはneutralなquery名へ変更し、呼び出しadapter側でQuiz semanticsを表現する。
7. build runnerでDAO mixinを再生成し、旧generated path参照が0件であることを確認する。
8. repository／datasource／DAO contract testをCatalog配下へ移す。

### Stage 4: Catalog public readerとcompositionを新graphへ切り替える

1. 新Catalog datasource／Repositoryを使う`DriftCatalogReader`と`DriftConjugationReader`を実装する。
2. direction dispatch、unsupported能力、not-found、failure identityをlegacy adapterと同じtest suiteで比較する。
3. `catalogReaderProvider`／`conjugationReaderProvider`を新readerへ切り替える。
4. app compositionから`core/di/data/repository_di.dart`依存を除去する。
5. WordDetail integration testを実行し、detail、部分失敗、tab／Quiz button表示が変わらないことを確認する。
6. `legacy_catalog_*` adapter／mapperと対応testを削除または新名称へ置換する。

### Stage 5: Search integrationをCatalog側へ移す

1. 現行`SearchQueryDao`、`DriftSearchQueryRepository`、必要なenrichment helperをCatalog internalのSearch adapterへ移す。
2. core datasource／converter依存を新Catalog datasource／mapperへ置換する。
3. Search DIは`ISearchQueryRepository`としてapp compositionからadapterを受け取る。
4. Search application／presentationからCatalog internal importが0件であることを確認する。
5. primary、suggestion、enrichment部分失敗、stale response、paginationの既存testを同じfixtureで通す。
6. Catalog domain／public portからSearch importが0件であり、Search importがintegration adapter一か所に限定されることを確認する。

### Stage 6: Quiz candidateとQuiz gameを切り替える

1. Quiz candidate adapterを新Catalog conjugation datasourceへ接続する。
2. adapter／mapper／enrichmentから`legacy`名と旧core importを除去する。
3. `QuizGameViewModel`を`ConjugationReader`と`CatalogWordRef`入力へ切り替える。
4. provider、UI model、widgetを`CatalogConjugation`またはQuiz-owned projectionへ切り替える。
5. Quiz固有の英語tense／subject変換をQuiz側へ移し、Catalog internal enumを参照しない。
6. `IFetchEspConjugationUseCase`、input data、interactorへのQuiz参照が0件であることを確認する。
7. candidate選択からQuiz game表示までのwidget／view model regressionを実行する。

### Stage 7: coreのlegacy graphと混在DIを削除する

1. 未使用になった`core/application/usecase/fetch_dictionary`、`fetch_jpn_esp_dictionary`、`fetch_conjugation`を削除する。
2. coreのCatalog Repository interface／実装、datasource、converter、domain entityを削除する。
3. `core/di/data`からCatalog DAO／datasource／Repository providerを除去し、shared `databaseProvider`と順序7以降で必要なstatus providerを残す。
4. `core/di/usecase/usecase_di.dart`が空になる場合は削除し、Quiz固有DIはQuizへ残す。
5. `test/unit/core/application/catalog_fetch_usecase_test.dart`を削除し、同じcontractがCatalog reader testへ移管済みであることを確認する。
6. repository全体で旧symbol／旧path／`legacy_catalog`／`getQuizConjugacionByWordWithPage`参照が0件であることを確認する。

### Stage 8: regressionとboundary確認

1. Catalog port／domain／infrastructure／integration testを実行する。
2. WordDetail、Search、Quiz、Rankingのunit／widget testを実行する。
3. DB schema／migration／Web seeder／native database testを実行する。
4. WordStatus、Sync、guest migration testを実行し、共有DB graphが維持されることを確認する。
5. build runnerの再実行で差分が発生しないことを確認する。
6. 全体`flutter analyze`、format check、import boundary検査、`git diff --check`を実行する。

すべて0件を期待する。ただし最初の検査はCatalog自身を除外し、Catalog internal integration adapterからconsumer-owned portへの意図した逆向きimportは別のallowlist testで一か所ずつ許可する。`DatabaseProvider`とtable宣言に残るCatalog table symbolはschema runtimeの例外であり、業務entity／Repositoryの残存として扱わない。

- `DatabaseProvider.schemaVersion`が変わっていない。

- Esp→Jpn／Jpn→Espのword、dictionary、conjugation、status table名とcolumn名が一致する。

## 7. リスクと対策

### 大量のfile moveでbehavior差分が埋もれる

domain、infrastructure、consumer切替、cleanup、generated更新をstage／commit単位で分ける。移動stageではSQLやmappingを変更せず、neutral renameはcontract testがあるmethodだけに限定する。

### SearchがCatalog internalへ直接依存する

import先の機械置換を禁止し、`ISearchQueryRepository`をSearch-owned portとしてCatalog側adapterで実装する。boundary testでCatalog internal importがSearch配下に0件であることを固定する。

### Quiz gameだけ旧core活用entityが残る

candidate検索とは別にQuiz gameのprovider／view model／widgetを棚卸しし、`ConjugationReader`へ切り替えてからcore use caseを削除する。raw word IDからCatalog identityへの変換点を一か所に限定する。

### enum移動でDB値やUI表示が変わる

Catalog wire value、DB mapper、feature表示extension、Quiz英語mappingを分離し、旧enum全valueのtable-driven testを作る。`name`の偶然一致を永続化contractにしない。

### Drift DAO移動でgenerated codeが壊れる

sourceの`part` pathを先に更新し、build runnerで再生成する。generated fileを手編集しない。schema snapshotと二回目生成のclean diffで安定性を確認する。

### table宣言を同時に移してWordStatus／Rankingまで破壊する

共有database runtimeとschema declarationは本スライスに残し、Catalog DAOだけを移す。table registrationの物理整理は順序11で全ownerを揃えて実施する。

### legacy adapterと新readerが二重の正本になる

同じcontract test suiteを両実装へ通した後、compositionを一度に新readerへ切り替える。切替後はlegacy provider、adapter、mapper、test fixtureを削除し、参照0件を完了条件にする。

### `core/di/data`からstatusやQuiz英語datasetまで誤って削除する

providerをCatalog、WordStatus、Quiz English、shared databaseに分類してから編集する。本スライスではCatalog分類だけを移し、順序7〜8およびQuiz-owned datasetを保持する。
